<objective>
Build the engine's configuration layer: the TypeScript shape of an interaction
TYPE, the shape of a student-authored INSTANCE, and the pure resolver that
combines them into one session config. Transcribe today's four interview presets
and the case-play scenario pipeline into that shape so the engine has two real
consumers from day one.

Purpose: this is what makes Phase 13's success criterion 1 true — "a new
one-on-one interaction type ships as a config record plus prompts." Phases 14-16
add records here and nowhere else.
Output: `lib/engine/{types,registry,resolve}.ts` plus a verification script. No
existing route, component or page is touched by this plan.
</objective>

<task type="auto">
  <name>Task 1: Declare the engine's config types, including the four primitives' config shapes</name>
  <files>lib/engine/types.ts</files>
  <action>
Create `lib/engine/types.ts` declaring, with a file header comment stating that
adding an interaction type means adding a record in `registry.ts` and nothing
else:

- `RubricDimension` — `{ key: string; label: string; description: string }`.
- `SHARED_RUBRIC_DIMENSION_KEYS = ["visual", "vocal", "content", "behavioral"] as const`
  and `type SharedRubricKey = typeof SHARED_RUBRIC_DIMENSION_KEYS[number]`.
- `InteractionTypeConfig` with at minimum:
  - `slug: string`, `name: string`, `description: string`
  - `extraRubricDimensions: RubricDimension[]` — type-declared EXTRAS ONLY. The
    four shared dimensions are NOT declarable here; this is how REQ-72 is made
    structural. Add a doc comment saying so.
  - `prompts: { liveSystemPrompt: ... ; evaluatorPrompt: string; buildEvaluationContext: ... }`
    — model the live system prompt as a function of SESSION-CONSTANT inputs only
    (`ResolvedSessionConfig`), never a turn index/timestamp, and say so in a doc
    comment citing REQ-73 and `lib/interview/prompts.ts`'s existing cache
    contract.
  - `limits: { targetMinutes: number | null; targetQuestionCount: number | null }`
  - `terminationPolicy: TerminationPolicyConfig`
  - `visibleContext: VisibleContextConfig`
  - `outcome: OutcomeRecordConfig`
  - `timeBudget: TimeBudgetConfig`
  - `instance: { required: boolean }` — `true` for `case-study`, `false` for the
    interview presets.
  - `setupSteps: SetupStepDeclaration[]` — a declared list of step ids plus an
    optional custom-component marker, for the generic wizard REQ-70 builds in
    13-09. Declaration only; the wizard is not this plan's job.
- The four primitive CONFIG shapes as DECLARATIONS ONLY (their runtime lives in
  plan 13-03, which must import these, not redefine them):
  - `TerminationPolicyConfig` — who may end the session: at minimum
    `{ studentMayEnd: boolean; avatarMayEnd: boolean; avatarEndReasons: string[] }`.
    Model "avatar ends with a recorded reason" as first-class.
  - `VisibleContextConfig` — a GENERAL per-turn slice: a type declares what
    channels/keys of session state the avatar may see on a given turn. Do NOT
    model this as slide bookkeeping; slides are one future instance of it.
  - `OutcomeRecordConfig` — a type-declared JSON outcome shape (field keys +
    kinds), e.g. a negotiated price and equity.
  - `TimeBudgetConfig` — `{ totalSeconds: number | null; warnAtRemainingSeconds: number | null }`.
- `InstanceConfig` — the student-authored layer: a discriminated union over
  `kind`, with a `"case-study"` member carrying the existing S3 `CaseStudy`
  fields the scenario pipeline already snapshots (`caseId`, `caseName`,
  `background`, `avatars`, `criteria`) and a `"none"` member for typeless runs.
- `ResolvedSessionConfig` — the single object the rest of the engine consumes:
  the type's slug/name, the FULL rubric dimension list (four shared first, then
  extras), resolved limits, the four primitives, the resolved instance, and the
  interview-style `customization` passthrough where present.

Types only in this file — no runtime logic beyond `as const` arrays.
  </action>
  <verify>`npx tsc --noEmit` is clean for this file. `grep -c "terminationPolicy\|visibleContext\|outcome\|timeBudget" lib/engine/types.ts` is non-zero for each.</verify>
  <done>`lib/engine/types.ts` compiles and declares `InteractionTypeConfig`, `InstanceConfig`, `ResolvedSessionConfig` and all four primitive config shapes. A type record has no way to declare or remove the four shared rubric dimensions.</done>
</task>

  can end a session, and this plan preserves that for interviews.
  `visibleContext`: the permissive/everything-the-session-knows default.
  `outcome`: no declared fields. `timeBudget`: derived from the preset's
  `targetMinutes`, `warnAtRemainingSeconds: null` (no warning exists today).
- One `case-study` record: name/description matching today's Case Studies
  product copy, `instance.required: true`, `extraRubricDimensions: []`,
  `terminationPolicy` identical to the interview presets (student-only),
  `limits.targetMinutes: null` (a scenario has no target today),
  `prompts.evaluatorPrompt` referencing the existing `SCENARIO_EVALUATOR_PROMPT`
  export from `lib/scenario/prompts.ts` and `buildEvaluationContext` returning
  the `caseName`/`background`/`characters`/`authorCriteria` shape
  `buildScenarioEvaluationUserMessage` already sends. Import these; do not copy
  the prompt text, and do not edit `lib/scenario/prompts.ts`.

`lib/engine/resolve.ts`: export `resolveSessionConfig(typeSlug, input)` returning
`{ ok: true; config: ResolvedSessionConfig } | { ok: false; reason: ... }`.

- PURE and deterministic — no I/O, no Date.now(), no randomness. It is re-run on
  every chat turn (the same discipline `lib/interview/customization.ts` documents
  for `resolveInterviewType`), which is what keeps the OpenAI prefix cache safe.
  State this in the file header.
- Unknown slug returns `ok: false`, never throws (matches REQ/Phase-4's
  "unknown type slug is handled, not crashed on").
- A type with `instance.required: true` and no instance returns `ok: false`.
- The resolved rubric dimension list is ALWAYS
  `[visual, vocal, content, behavioral, ...type.extraRubricDimensions]` in that
  order, with duplicate extra keys rejected as `ok: false`.
- For interview types, accept the existing client `customization` payload and
  resolve it by calling the existing `resolveInterviewType` /
  `resolveCustomizationRecord` from `lib/interview/customization.ts` — that
  module stays the single place interview picker fields are validated. Do not
  reimplement its validation.
