<non_negotiables>
**Read research Section A's divergence list before writing a line. Every item on it
is a REQ-69 "preserve, do not converge" obligation:**

1. **Scenario has NO checkpoint.** The engine exposes a checkpoint endpoint; the
   `case-study` type simply never calls it, and the engine must not issue one on its
   behalf. Giving scenarios a checkpoint "for free" would make a scenario resumable
   where today it is not — an observable behavior change. Express this as a declared
   property of the type (e.g. `checkpointing: "client-driven" | "none"`) so the
   intent is readable, and assert it.
2. **Start-side shape differs.** Interview start: ONE Prisma write, ZERO S3 writes.
   Scenario start: reads the scenario from S3 (`s3Storage.getCase`, not Prisma),
   enforces its own playability check (`ownerId` present AND (own OR published)),
   does a Prisma write, then creates an S3 `InteractionLog`, and **if the S3 write
   fails it explicitly deletes the just-created Prisma row** (the no-orphan-row
   discipline), then does a SECOND Prisma write for `interactionLogId`+`studentEmail`.
   Preserve both shapes exactly, including the compensating delete and the
   two-write sequence.
3. **Finish-side status flip differs.** Interview finish flips `status: PENDING` in
   the request path; scenario finish does NOT (its runner does). Scenario finish
   awaits its metrics write BEFORE `waitUntil` so the runner's own row read sees
   them. 13-05's runner now flips PENDING itself as its first write, which makes
   both orders safe — but keep each type's request-path behavior as it is today
   rather than normalizing it.
4. **Finish still returns 202 fast** (~200ms target) with evaluation in `waitUntil`,
   and a double-submit still returns **409 WITH the reportId and status** so the
   client can still navigate to the report.
5. **Scenario's transcript still comes from the S3 `InteractionLog`** written by
   `/api/interaction/save` during the session. Do NOT touch
   `app/api/interaction/{start,finish,save,get}/route.ts` — out of scope, and
   `save`/`get` also serve the legacy admin-case pipeline.
6. Camera mode is resolved SERVER-SIDE and forced OFF when there is no consent, for
   every type. The identical six-line consent read currently duplicated in both
   start routes moves into `lib/engine/session.ts` — one copy, same behavior.
7. New rows go to `InteractionReport` ONLY. Do not dual-write the legacy tables.
8. Do not run any migration in this plan. Do not touch `prisma/schema.prisma`.
</non_negotiables>

<task type="auto">
  <name>Task 1: The engine session lifecycle</name>
  <files>lib/engine/session.ts</files>
  <action>
Read all five existing session routes end to end first, then create
`lib/engine/session.ts` exporting three handlers that take an authenticated
`userId` plus a parsed request body and return a plain result object (the routes do
the auth + NextResponse wrapping, so the handlers stay unit-testable):

- `startSession({ userId, typeSlug, instanceId, customization, cameraModeRequest })`:
  resolve the config via `resolveSessionConfig` (400-equivalent on unknown slug);
  read `User.videoAnalysisConsentAt` once and resolve `cameraMode`, forcing OFF
  without consent; then run the type's declared start shape:
  - types with `instance.required: false` (the four interview presets): ONE
    `interactionReport.create` with `typeSlug`, `status: IN_PROGRESS`, `cameraMode`,
    `metricsConsentAt`, and `inputSnapshot` built as the locked
    `{kind:"interview", ...}` shape from the RESOLVED customization. No S3 write.
  - `case-study`: read the scenario from S3 via the existing `s3Storage.getCase`;
    enforce the existing inline playability rule (reject when `ownerId` is absent,
    or when the scenario is neither the caller's nor published); create the row with
    `inputSnapshot` as the locked `{kind:"scenario", ...}` REQ-33 snapshot
    (snapshotted at start, never re-fetched later); create the S3 `InteractionLog`
    via `s3Storage.saveInteractionLog`; on S3 failure DELETE the just-created row
    and return the failure; then a second update writing `interactionLogId` and
    `studentEmail`.
  Return `{ reportId, cameraMode }` for both — the shape both clients expect today.
- `checkpointSession({ userId, reportId, turns })`: ownership via
  `findFirst({ id, userId })`, reject unless `IN_PROGRESS`, rebuild the FULL
  transcript from the client-sent turns via the existing `buildInterviewTranscript`
  from `lib/interview/transcript.ts`, write it to S3 via
  `s3Storage.saveInterviewTranscript`, update `turnCount` + `transcriptKey`. No LLM
  calls. Reject with a clear error if the resolved type declares
  `checkpointing: "none"` — a case-study session must never land here.
- `finishSession({ userId, reportId, turns, metricsPayload, log, terminationReason, outcome })`:
  ownership + `IN_PROGRESS` check; double-submit returns a result carrying
  `{ conflict: true, reportId, status }` so the route can answer 409 with them.
  Then dispatch on the type's declared finish shape, reproducing each of today's
  orderings (see non-negotiable 3), and in BOTH shapes:
  - ALWAYS call `parseMetricsPayload` + `toMetricsJsonInput` from
    `lib/metrics/ingest.ts` and persist `visualMetrics`/`vocalMetrics`/`cameraMode`.
    This is REQ-72's structural guarantee — there is no branch in which a type skips
    it.
  - Persist `terminationReason` through `resolveTermination` (rejected terminations
    write null) and `outcome` through `validateOutcome` (an invalid outcome is
    rejected and written as null, never half-written).
  - `waitUntil(runAndPersistEvaluation({ reportId }))`, return `{ accepted: true, reportId }`.
  </action>
  <verify>`npx tsc --noEmit` clean. `grep -n "parseMetricsPayload" lib/engine/session.ts` appears in a path both type shapes reach — confirm by reading, and confirm there is no `if` that can skip it.</verify>
  <done>One module holds the whole session lifecycle for every type; each type's start/finish ordering divergence is explicit and preserved; metrics parsing is unconditional.</done>
