Columns (read the existing two models first and mirror their types exactly):
- `id String @id @default(uuid())`, `userId String` + `user User @relation(fields: [userId], references: [id], onDelete: Cascade)`
- `typeSlug String` — engine type slug: `general|technical|consulting|early-career|case-study`
- `status InterviewReportStatus @default(IN_PROGRESS)` — **do NOT rename the enum.**
  It is shared by both existing models today; renaming it is a discretion item and
  the answer for this phase is NO, because a rename touches every importer and
  buys nothing. Add a comment noting the name is historical.
- `inputSnapshot Json?` — nullable so an `IN_PROGRESS` row can exist before the
  snapshot is complete, matching today's behavior where snapshot columns are
  written at start.
- `scores Json?` — the dimension-keyed map `{visual, vocal, content, behavioral, ...}`.
- `transcriptKey String?` AND `interactionLogId String?` AND `studentEmail String?`
  — **keep all three as separate nullable columns; do NOT converge them.** Research
  Open Question 3's recommendation, and CONTEXT.md leaves it to discretion: the two
  pointers resolve through different `s3Storage` accessors
  (`getInterviewTranscript(userId, reportId)` vs
  `getInteractionLog(studentEmail, caseId, logId)`) with different required
  context, so converging buys a tagged union and costs read-path branching for no
  requirement. `studentEmail` is retained precisely because the scenario S3 read
  cannot resolve without it. Write this rationale as a schema comment.
- `turnCount Int @default(0)`
- `cameraMode String?`, `visualMetrics Json?`, `vocalMetrics Json?`,
  `visualUnscoredReason String?`, `vocalUnscoredReason String?`,
  `metricsConsentAt DateTime?` — copy the existing comments verbatim from
  `InterviewReport`, including the "null = pre-Phase-10 row" note.
- `reportStructured Json?`, `reportMarkdown String? @db.Text`,
  `failureReason String? @db.Text`, `evalModel String?`
- `terminationReason String?` — the recorded reason an avatar-initiated end
  produces (REQ-62). Nullable; null means the session ended normally.
- `outcome Json?` — the type-declared outcome record (REQ-64). Nullable.
- `startedAt DateTime @default(now())`, `completedAt DateTime?`,
  `createdAt DateTime @default(now())`, `updatedAt DateTime @updatedAt`
- Indexes: `@@index([userId, createdAt])` and `@@index([userId, typeSlug])`.

Then generate the migration against the LOCAL dev DB only:
