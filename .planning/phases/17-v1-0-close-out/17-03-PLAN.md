  <action>
Read `app/api/interaction/chat/route.ts` around lines 480-660 FIRST to learn the exact
live call shapes, then create `scripts/verify-deck-visible-context.ts`.

Build one 8-slide deck fixture in memory whose slide `i` text is
`SENTINEL-SLIDE-{ii}-K7QX plus a sentence of filler`. Resolve a `pitch-deck` session
config carrying those `slideTexts` through the real resolver
(`resolveSessionConfig`, see `lib/engine/resolve.ts:159` which copies
`type.visibleContext` onto the resolved config) so the test is live rather than
hand-constructed. Sections:

1. **The test is live.** The resolved config's `instance.kind === "pitch-deck"`, its
   `slideTexts` carry all 8 sentinels, and `config.visibleContext` is
   `DECK_VISIBLE_CONTEXT` with `visibleChannels` naming the `slides` channel (NOT `"*"`
   — print the posture; `"*"` would mean no gating at all and must fail this section).
2. **Nothing shown yet.** `mark === null` → `resolveRevealedSlides` returns `[]`, and
   `buildTurnMessages` output contains **zero** occurrences of `K7QX`. A deck session's
   turn 1 before any slide is advanced must leak nothing at all.
3. **Forward sweep — the unreached-slide half.** For each `mark` in 0,1,2,…,7: ratchet
   via `ratchetHighWaterMark({ stored, requested: mark, slideCount: 8 })`, call
   `resolveRevealedSlides`, build the full turn messages via `buildTurnMessages` with
   `revealedSlides` and `slideCount: 8`, and assert on
   `JSON.stringify(builtMessages)`:
   - every sentinel `0..mark` is PRESENT,
   - every sentinel `mark+1..7` is ABSENT — zero occurrences, each checked individually
     so the failure message names the leaking slide.
   Print the tail block at `mark = 2` in full so a human can read what the investor
   actually receives.
4. **Backward navigation does not un-show.** Advance to `mark = 6`, then feed
   `requested: 2` back into `ratchetHighWaterMark`. Assert the returned mark is still 6
   and `advanced === false`, then rebuild the turn and assert sentinels 0-6 are ALL still
   present and sentinel 7 is still absent. This is the second half of Phase 14
   criterion 3 and the reason the high-water mark exists at all
   (`lib/pitch/slide-reveal.ts` header comment).
5. **A client cannot jump ahead.** Feed hostile `requested` values into
   `ratchetHighWaterMark` at `stored: 2`: `99`, `8`, `7.9`, `-1`, `NaN`, `Infinity`,
   `"7"`, `null`, `undefined`, `{}`. Assert the returned mark never exceeds
   `max(stored, slideCount - 1)` and never exceeds `stored` for the non-numeric cases,
   then rebuild the turn for each and assert no sentinel above the legitimate mark
   appears. `ratchetHighWaterMark` is documented as the only place in the repo that reads
   a client-supplied slide index — section 7 proves that claim mechanically.
6. **The system prompt is clean and session-constant.** For marks 0, 3 and 7, the
   assembled SYSTEM prompt specifically (not the tail block) contains zero sentinels and
   is byte-identical across all three marks. Slide text living in the system prompt would
   break REQ-73's prefix cache as well as leaking; `lib/pitch/slide-reveal.ts` carries
   that warning on `buildSlidesTailFragment`.
7. **Grep backstop for the single-reader claim.**
   `grep -rn "slideHighWaterMark\|slideTexts" app lib --include="*.ts" --include="*.tsx"`
   — classify every hit and assert that the only place a client-supplied slide index is
   read into a mark is `ratchetHighWaterMark`. Print the classification table.
8. **The evaluator DOES see the shown slides.** `buildDeckEvaluationContext` for a
   session at `mark = 6` contains sentinels 0-6. Print the context. Without this, slide
   coverage and the "talk track tracked the slide" dimension are unscoreable and the
   exclusion has gone too far — this is the mirror of 16-09's section 7.
9. **No other type is affected.** Place the sentinels into an interview session's
   session state and assert behavior is unchanged from the permissive `"*"` posture those
   types declare (`lib/pitch/elevator-type.ts:68`,
   `lib/difficult-conversation/conversation-type.ts:140`). This guards against the deck
   gating being implemented as a global filter.

Every section prints `ok:`/`FAIL:` per assertion and `process.exit(1)` on any failure.
  </action>

Every pre-existing verify script named in `16-VALIDATION.md` Block A still exits 0 (spot-check `verify-engine-config`, `verify-engine-primitives`, `verify-pitch-types`).</verify>
