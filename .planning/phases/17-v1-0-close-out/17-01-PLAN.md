<objective>
Remove `prisma migrate deploy` from `vercel.json`'s `buildCommand`, and in the same plan
leave behind the procedure that replaces it.

Purpose: `HANDOFF.md §3`, `13-MIGRATION-HANDOFF.md §2` and REQ-67 all state that no agent
applies a migration and that a human runs `prisma migrate deploy` against a shared
database. That has not described this project since `vercel.json` gained
`prisma migrate deploy` in its `buildCommand`: every deployment has applied pending
migrations automatically and unreviewed, and a preview build on 2026-10-04 applied
`add_interaction_report_title` to a database that already held the first `DROP TABLE` in
this project's history — no human run, no `pg_dump`. The user was offered the other
resolution (amend the docs to bless CI-applied migrations) and rejected it: the pipeline
changes to match the discipline, not the reverse.

The removal alone would be a regression. With CI no longer migrating, a schema change must
be applied deliberately BEFORE the deploy that depends on it, or the app serves 500s on a
missing column. So the procedure that replaces the automatic behaviour ships in this same
plan. Phase 18 is its first consumer.

Output: a `buildCommand` that touches no database, and `docs/MIGRATIONS.md`.
</objective>

<task type="auto">
  <name>Task 2: Write docs/MIGRATIONS.md — the procedure that replaces the automatic apply</name>
  <files>docs/MIGRATIONS.md</files>
  <action>
Create `docs/MIGRATIONS.md` (new `docs/` directory). This document is the whole reason the
removal in Task 1 is allowed to ship: with CI no longer migrating, anyone who deploys a
schema change without applying it first gets 500s on a missing column. Write it for the
person who has to do that in Phase 18, not as a policy statement.

Required sections, in this order:

1. **Status / why this exists.** One short paragraph: as of 2026-10-04 `vercel.json`'s
   `buildCommand` no longer runs `prisma migrate deploy` (REQ-74; cite Task 1's commit).
   Deployments no longer apply migrations. State the consequence in one blunt sentence:
   **a migration must be applied to a target database before the deploy that depends on
   it, or that deploy serves 500s on a missing column.** Cite `HANDOFF.md §3` for the
   history and note the 2026-10-04 preview build that applied a migration unreviewed to a
   database already holding a `DROP TABLE`.

2. **Who may apply what, to which database.** A small table. Rows:
   - Local dev DB (`leadership_avatar_dev`, localhost): an agent MAY run
     `prisma migrate dev` / `migrate deploy` / `migrate status` freely.
   - Shared Lightsail DB: **human only.** No agent connection of any kind, including a
     read-only `SELECT`. Cite `HANDOFF.md §3` and `13-MIGRATION-HANDOFF.md §2`.
   - Vercel Preview / Production `DATABASE_URL`: **human only**, same rule, and note that
     what the Production secret points at is tracked as an open question in
     `HANDOFF.md §3` (17-02 closes it).
   Make the rule's scope explicit so it stops being quietly false: it binds agents and
   humans-acting-through-agents; it never bound CI, and the reason it is now also true of
   CI is that CI no longer migrates.

3. **The procedure.** Numbered, copy-pasteable, with `DATABASE_URL` as a placeholder and
   NO real credentials anywhere in the file:
   1. Merge/land the migration files in `prisma/migrations/` WITHOUT deploying
      (`git.deploymentEnabled` is `main`-only, so a feature branch is safe).
   2. Human checks pending state against the target:
      `DATABASE_URL="<target>" npx prisma migrate status`
   3. For anything destructive (see §4): `pg_dump` first, with the command.
   4. Human applies: `DATABASE_URL="<target>" npx prisma migrate deploy`
   5. Human re-checks: `migrate status` must report `Database schema is up to date!`
   6. Only then deploy the code that depends on it.
   7. Record the run — target, date, who, the `migrate status` output — appended to
      `HANDOFF.md §3`'s table.

4. **Which changes are safe to apply ahead of the deploy, and which are not.** This is the
   section that prevents the obvious new failure mode:
   - **Additive (safe, apply before the deploy):** new table, new nullable column, new
     index, new enum value. Old code ignores what it does not know about. This is the
     shape every migration in this project has had except one.
   - **Destructive / narrowing (needs expand→contract across TWO deploys):** `DROP
     TABLE`/`DROP COLUMN`, adding `NOT NULL` to an existing table, rename, type change.
     Deploy 1 ships code that no longer reads the old shape; THEN apply the migration;
     THEN deploy 2. Name `20261004040000_drop_legacy_report_tables` as the project's one
     precedent and that it was only safe because both tables were empty.

5. **If you get it wrong.** Symptom: 500s referencing an unknown column or relation right
   after a deploy. Cause: the deploy landed before its migration. Fix: apply the migration
   to that database (step 3.4) — no redeploy is needed, the running build picks up the
   column on the next query. Do not "fix" it by putting `migrate deploy` back in
   `buildCommand`.

6. **Phase 18 — first consumer.** Phase 18 adds disengagement/termination fields, so its
   plan MUST contain an explicit human migration step placed before the deploy that reads
   them, following §3. One sentence telling Phase 18's planner to carry a
   `checkpoint:human-action` for the apply rather than assuming CI handles it.

Keep it under ~120 lines. Prose, tables and fenced commands only — no new tooling, no
scripts, no npm script additions.
  </action>

  <done>`docs/MIGRATIONS.md` tells a human, in order, how to apply a schema change to a named target before the deploy that needs it; distinguishes additive from destructive changes with the expand/contract sequence; states who may connect to what; says what to do when a deploy beats its migration; and names Phase 18 as the first consumer with the checkpoint it needs.</done>
