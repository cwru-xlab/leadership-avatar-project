answered with numbers from the current single-model baseline rather than a
guess after four models are already in.

awaited, and a one-line per-session cost report.

  <name>Task 1: Make stop() async with a bounded drain</name>
  <files>lib/metrics/visual-capture.ts</files>
  <action>
Change `VisualCaptureHandle.stop` from `stop(): VisualMetrics | null` to
`stop(timeoutMs?: number): Promise<VisualMetrics | null>` and make the
implementation `async`.

Mirror `lib/metrics/vocal-capture.ts`'s `drain(timeoutMs)` pattern (lines
378-397) exactly: a module-level `DEFAULT_STOP_TIMEOUT_MS` constant (use 1500),
and any awaited teardown wrapped in `Promise.race([work, new Promise(resolve =>
setTimeout(resolve, timeoutMs))])` so a hung teardown can never block the End
button. Today there is nothing async to await inside — that is fine and
deliberate: introduce the bounded-race helper now (an inline
`async function closeEngine(timeoutMs: number): Promise<void>` that currently
only calls `landmarker?.close()` inside a try/catch) so plan 12-03 has a seam
to drop the worker round-trip into without touching call sites a second time.

Ordering constraints that must NOT change:
- `stopped = true` and `stopInterval()` still happen FIRST and synchronously,
  before any await, so no tick can run concurrently with metric assembly.
- The video element teardown (`pause`, `srcObject = null`, `remove`) stays
  synchronous and stays before the first await.
- Metric assembly (`computeVisualRates`, `closeWindow`, `extractEpisodes`,
  posture flags, the returned object) is unchanged — do not touch any
  arithmetic in this plan.

Update the doc comment on `stop` to say the returned promise is bounded and
never rejects, and that the caller still owns the MediaStream.
  </action>
  <verify>`npx tsc --noEmit` reports the two expected call-site errors in `components/interview/InterviewSessionShell.tsx` and `app/case-play/[caseId]/page.tsx` and no others in `lib/metrics/`. `grep -n "Promise<VisualMetrics | null>" lib/metrics/visual-capture.ts` matches both the interface and the implementation.</verify>
  <done>`stop()` returns a promise that resolves (never rejects) within `timeoutMs`, with interval teardown and video teardown still synchronous and ahead of every await.</done>

delay releasing the camera tracks.** The LED going out is what a student sees;
it must not depend on inference shutdown.

  its body to capture the handle into a local, null the ref, release the tracks
  and clear `cameraStream` FIRST, then fire the engine stop as
  `void handle?.stop().catch(() => {})` — deliberately not awaited, because its
  three callers (unmount effect ~line 335, `handleLeave` ~line 804, the
  post-finish cleanup ~line 880) discard the metrics entirely.
- `handleEnd` (line ~854) is the one path that needs the value. Replace
  `visual = visualCaptureRef.current?.stop() ?? null;` with
  `visual = (await visualCaptureRef.current?.stop()) ?? null;` keeping the
  existing try/catch. Null `visualCaptureRef.current` immediately afterwards so
  the later `releaseVisualCapture()` (line ~880) cannot double-stop — note
  `stop()` is already idempotent via the `stopped` flag, so this is belt and
  braces, not load-bearing.
