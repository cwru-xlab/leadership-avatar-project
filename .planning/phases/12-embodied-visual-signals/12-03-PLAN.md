<objective>
Move inference off the main thread and put a staggered, round-robin scheduler in
place — with the face model as the only tenant — so the frame budget is proven
before plan 12-05 adds three more models to it.

Purpose: REQ-57 is a hard ordering constraint, not an optimisation. Four models
at 6 Hz cannot coexist with the HeyGen WebRTC stream on one thread, and the
research found exactly one community precedent for running tasks-vision in a
worker plus one real interop pitfall (`importScripts` is invalid in an
ES-module worker). So this plan de-risks the loading path with a spike FIRST,
migrates the single existing model behind a fallback, and gates on a live
session before any new detector exists. If the worker path cannot be made to
work, that is discovered here — with one model to roll back, not four.
Output: a working worker host, a scheduler with one registered model, and a
human-verified live session.
</objective>

<task type="auto">
  <name>Task 2: Migrate face inference into the worker behind a staggered scheduler and a main-thread fallback</name>
  <files>lib/metrics/visual-capture.worker.ts, lib/metrics/visual-capture.ts</files>
  <action>
Define a small typed message contract and move the `detectForVideo` call across
it, leaving ALL accumulation and derivation on the main thread.

Worker side (`visual-capture.worker.ts`):
- `init` message: `{ models: ["face"], delegate: "GPU" | "CPU" }` → create the
  requested landmarkers, reply `{ type: "ready", delegate }` or
  `{ type: "init-error", reason }`. Keep the existing GPU-then-CPU fallback
  semantics — attempt GPU, fall back to CPU, and report which one won so the
  existing `[visual-capture] engine started` diagnostic keeps telling the truth.
- `detect` message: `{ bitmap: ImageBitmap, model: "face", timestamp: number }`
  → run that ONE model, reduce its result to scalars, `bitmap.close()`, and
  reply with a scalar-only payload. For the face model the payload is exactly
  what `runTick` needs today and nothing more: `{ faceCount, primary: { minX,
  maxX, minY, maxY, centerX, centerY } | null, yawDeg, pitchDeg, poseAvailable }`.
  The primary-face selection (largest bounding box) and the head-pose matrix
  decode move INTO the worker, because that is what keeps the landmark arrays
  from ever crossing back. Port the existing logic verbatim — do not re-derive
  the thresholds or the yaw/pitch maths, which live on the main thread as
  constants and must stay there (the worker returns raw degrees; the main thread
  compares them to `FORWARD_YAW_LIMIT_DEG`/`FORWARD_PITCH_LIMIT_DEG`).
- `close` message → close every landmarker, reply `{ type: "closed" }`.
- A header comment restating REQ-58 for this file: the ImageBitmap is closed on
  the same message that received it, no landmark array is retained past the
  call, and the only thing ever posted back is a flat object of numbers and
  booleans.

Main-thread side (`visual-capture.ts`):
- Keep the 6 Hz `setInterval`. Replace the direct `landmarker.detectForVideo`
  call with: `createImageBitmap(videoEl)` → `postMessage({...}, [bitmap])` →
  on reply, feed the scalars into the SAME accumulators that exist today. All
  existing guards stay exactly where they are: the track-`readyState` check, the
  `videoEl.readyState < 2 || videoWidth === 0` skip (still not an error), the
  `MAX_CONSECUTIVE_DETECT_ERRORS` counter, the face-state debounce.
- **Back-pressure:** never allow more than one outstanding `detect` per model.
  If the previous reply has not arrived, skip this tick entirely — count it as a
  dropped tick in 12-01's instrumentation, NOT as a processed sample and NOT as
  a detect error. A queue would turn a slow frame into unbounded latency and
  would stamp stale measurements onto later windows.
- **Staggered round-robin scheduler:** introduce the structure now with one
  tenant. A `const SCHEDULE: ModelId[]` array consulted by tick index
  (`SCHEDULE[tickCount % SCHEDULE.length]`), currently `["face"]` so face still
  samples at the full 6 Hz and this plan changes no measurement. Document that
  12-05 extends this array, that each model's effective rate becomes
  `6 / SCHEDULE.length` Hz, and why that is acceptable: episode windows are 5
  seconds (`EPISODE_WINDOW_SECONDS`), so per-model temporal resolution well
  below 6 Hz still localises an excursion usefully.
- **Fallback:** if worker construction or `init` fails, or `ready` does not
  arrive within a bounded timeout (2000ms), log one `console.info` and run the
  existing main-thread `initLandmarker` path unchanged. A worker that will not
  start must degrade to Phase 10 behaviour, never to `analyzer_error` — a
  technical fallback must not be reported to a student as poor performance
  (REQ-42's discipline).
- Wire worker teardown into the `closeEngine(timeoutMs)` seam 12-01 created:
  post `close`, race the `closed` reply against the timeout, then
  `worker.terminate()` unconditionally.
- Update the `[visual-capture] frame budget` line's `models` field and add
  `thread: "worker" | "main"` so a walkthrough can tell which path ran.
  </action>
  <verify>`npx tsc --noEmit` clean. `npx tsx scripts/verify-visual-metrics.ts` still exits 0 (the pure surface is untouched). Live `npx next dev`: a camera-on interview logs `thread: "worker"`, the self-view banner still flips correctly when you leave frame, and the finish POST carries a populated `visual` block. Then force the fallback (temporarily rename the worker URL) and confirm the session still measures and logs `thread: "main"`.</verify>
  <done>Face inference runs in the worker with one-outstanding-request back-pressure, a scheduler array holding one model, and a proven degrade-to-main-thread path; metrics for the same behaviour match the pre-worker run within sampling noise.</done>
</task>
