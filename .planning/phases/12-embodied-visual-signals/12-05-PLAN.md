<objective>
Add the three remaining detectors — pose, hands and object (phone) — inside the
worker and behind the scheduler proven in 12-03, each reduced to per-tick scalars
on the main thread.

Purpose: this is where the body actually becomes visible. Separate
`PoseLandmarker` + `HandLandmarker` runners are used rather than
`HolisticLandmarker`, because the installed `@mediapipe/tasks-vision@1.0.1`
exposes no `numPoses`/`numHands` on `HolisticLandmarkerOptions` — it is
single-subject by construction and therefore cannot honour the multi-person
discipline the face pipeline already enforces. This plan produces raw per-tick
readings only; the derivations (baseline, drift, bands, episodes) are plans 12-06
and 12-07, so a budget problem surfaces before any derivation work is built on
top of it.
Output: four vendored models, three new runners, a four-way stagger, and a live
budget re-proof.

  <files>lib/metrics/visual-capture.worker.ts</files>
  <action>
Register three more models in the worker's `init` handler, each with the same
GPU-then-CPU delegate fallback as the face runner:
- `PoseLandmarker.createFromOptions(..., { numPoses: 2, runningMode: "VIDEO",
  modelAssetPath: "/mediapipe/pose_landmarker_lite.task" })`
- `HandLandmarker.createFromOptions(..., { numHands: 4, runningMode: "VIDEO",
  modelAssetPath: "/mediapipe/hand_landmarker.task" })` — four, because two
  people in frame have four hands and the point is to be able to tell whose are
  whose, not to silently average them.
- `ObjectDetector.createFromOptions(..., { scoreThreshold: PHONE_SCORE_THRESHOLD,
  runningMode: "VIDEO", modelAssetPath: "/mediapipe/efficientdet_lite0.tflite" })`

Each `detect` reply must be scalars only. Define per-model reply shapes:

**pose** → `{ poseFound: boolean, visible: { shoulderLine: boolean, forwardHead:
boolean, torsoLean: boolean, torsoOpenness: boolean }, shoulderTiltDeg: number |
null, forwardHeadOffset: number | null, torsoLeanDeg: number | null,
torsoOpennessRatio: number | null, shoulderMidX: number | null, shoulderMidY:
number | null, shoulderWidth: number | null }`
- Primary-subject selection: replicate the face pipeline's rule exactly — compute
  a bounding box per detected pose (reuse the `boundsOf` approach) and pick the
  LARGEST by area. Index order is not stable between frames, so trusting index 0
  would interleave two people's measurements inside one student's score without
  ever looking wrong. Copy the existing explanatory comment's reasoning.
- Visibility gating per metric, using each landmark's `visibility` field against
  `LANDMARK_VISIBILITY_FLOOR`: shoulderLine needs 11 and 12; forwardHead needs 0
  plus at least one of 7/8; torsoLean and torsoOpenness need 23 and 24. When a
  group is not visible, return `null` for its reading and `false` for its
  visibility flag — never a substituted or extrapolated value. A head-and-
  shoulders webcam framing will usually fail the hip gate, and that is the
  correct outcome: partial feedback beats faked feedback.
- Angles: shoulder tilt is the angle of the 11-12 line from horizontal, in
  degrees; forward-head offset is the nose's horizontal/vertical displacement
  from the shoulder midpoint, normalised by shoulder width so it does not change
  when the student moves closer to the camera. Document the normalisation —
  without it, leaning in would read as a posture change.

**hands** → `{ handCount: number, primary: Array<{ wristX, wristY,
fingertipSpanX, fingertipSpanY, aboveShoulder: boolean | null, nearFace: boolean
| null }> }` with at most TWO entries, selected as the two hands whose wrists are
nearest the primary pose's shoulder midpoint when a pose reading exists for the
same tick, falling back to the two largest hand bounding boxes otherwise. State
in a comment that this is the hands analogue of largest-face selection and that
the fallback is accepted risk (the research's open question 2: cross-model
subject identity is not guaranteed, bounding-box area is a reasonable proxy for
who is at the machine, and building spatial cross-referencing would be new
complexity for a sub-10% edge case).
- `aboveShoulder` compares wrist y against the primary pose's shoulder y in the
  same normalised image space — valid because both landmark sets use normalised
  image coordinates. Return `null`, not `false`, when no shoulder reading is
  available this tick.
- `nearFace` uses the face runner's most recent primary bounding box expanded by
  `HANDS_NEAR_FACE_RADIUS`; `null` when no face box is available.

**object** → `{ phonePresent: boolean, phoneScore: number }` — run the detector,
keep only detections whose category name is `"cell phone"`, and reduce to the
highest score. Nothing else from the 80-class set is retained; do not return the
category list.

Every reply must close its ImageBitmap and must not retain any landmark array.
Extend this file's REQ-58 header comment to cover the three new runners
explicitly.

  `["face", "pose", "face", "hands", "face", "object"]`: face keeps roughly half

- Add independent accumulators, mirroring the existing counter style, and keep
  them structurally separate from each other the way `speakingSamples` and
  `listeningSamples` are:

    `VISUAL_POSTURE_SIGNALS` entry), running sums for each angle reading
  - hands: `handSamples`, `handsDetectedSamples`, `handsAboveShoulderSamples`,
    `handsNearFaceSamples`, plus the previous tick's wrist positions and a
    displacement sum — the gesture-amplitude raw material, tracked the same way
    `lastCenter`/`movementSum` already tracks face motion

    not derived from the gesture counters. Fidgeting is a distinct low-amplitude
    high-frequency band; deriving it from the gesture accumulator would make the
    two signals correlate 1:1 and let fidget motion quietly inflate a scored
    gesture rate.

- Extend the per-window `CaptureWindow` interface with the window-level means and

  alongside the existing fields. Keep `windowTrips` untouched in this plan — new
  cases land with their thresholds in 12-06/12-07.
- Update the `[visual-capture] frame budget` log: `models: 4`, plus per-model
  mean tick cost and per-model dropped counts, so the checkpoint can see WHICH
  model is expensive rather than only the total.
