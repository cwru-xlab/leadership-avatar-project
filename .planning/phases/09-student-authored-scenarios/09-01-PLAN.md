<task type="auto">
  <name>Task 1: Add real ownership to the CaseStudy shape</name>
  <files>types/index.ts</files>
  <action>
In `types/index.ts`, add ONE optional field to the `CaseStudy` interface (currently at
lines ~202-220). This is the only type change the phase needs — additive and optional,
so every already-shipped admin case and every existing consumer still compiles.

- `ownerId?: string` — the authenticated `User.id` (Postgres uuid, as returned by
  `getCurrentUser` in `lib/auth.ts`) of the student who authored this scenario.

Doc comment must state all of:
- Presence marks the object as a STUDENT-AUTHORED SCENARIO; absence means a legacy
  admin-authored case study. This single field is the discriminator `/case-play` uses
  to split its two sections.
- It is set SERVER-SIDE from the session cookie at creation, is immutable afterwards,
  and is NEVER read from a client-supplied request body.
- `createdBy` remains a display-only string with unchanged semantics and is NOT an
  ownership model; `cohortIds` is untouched dead weight owned by Phase 11.
- Because it is a plain field on the object (not a relation), a future "fork" action
  can copy a scenario and overwrite `ownerId` with no schema change — REQ-30's
  "model must not preclude forking" is satisfied by construction.

Do NOT change `CaseAvatar`. The scenario builder sources its character avatars from the
admin-curated `VideoAudioProfile` catalog and stores the existing `profileId`, so the
`/case-play` player's `loadAvatarConfig` needs no new branch and no new field exists to
get out of sync. (This deviates from an earlier research draft that proposed adding a
raw LiveAvatar `avatarId` to `CaseAvatar`; see 09-05 for the rationale.)

Do NOT remove or repurpose `cohortIds`, `createdBy`, `lastEditedBy`, or `published`.
Do NOT touch any other interface in this file.

<task type="auto">
  <name>Task 2: Add the ScenarioReport model and apply the migration to the local dev DB only</name>

  <action>
Add a `ScenarioReport` model to `prisma/schema.prisma`, structurally parallel to the
existing `InterviewReport` (lines ~284-330), plus the `User` back-relation.

Fields:
```prisma
model ScenarioReport {
  id                 String                @id @default(uuid())
  userId             String

  // The S3 CaseStudy id this run played. Deliberately a bare String and NOT a
  // Prisma relation — the scenario lives in S3, not Postgres, and REQ-34 requires
  // this report to survive that scenario's deletion. There is nothing to cascade.
  caseId             String

  // Pointer back to the S3 InteractionLog this run produced, so the evaluator can
  // re-read the transcript without a second copy being written.
  // interactions/{studentEmail}/{caseId}/{logId}.json
  interactionLogId   String?
  studentEmail       String?

  status             InterviewReportStatus @default(IN_PROGRESS)

  turnCount          Int                   @default(0)

  // Nullable by design. Visual and Vocal stay null until Phase 10 builds a real
  // video/audio metrics pipeline. Enforced in code, never trusted from the model.
  visualScore        Int?
  vocalScore         Int?
  contentScore       Int?
  behavioralScore    Int?

  reportMarkdown     String?               @db.Text
  failureReason      String?               @db.Text
  evalModel          String?

  // REQ-33 run-time snapshot. Written once when the run is recorded; never updated
  // when the underlying scenario is later edited or deleted.
  caseName           String
  backgroundSnapshot String                @db.Text
  avatarsSnapshot    Json
  criteriaSnapshot   String?               @db.Text

  startedAt          DateTime              @default(now())
  completedAt        DateTime?
  createdAt          DateTime              @default(now())
  updatedAt          DateTime              @updatedAt

  user User @relation(fields: [userId], references: [id], onDelete: Cascade)

  @@index([userId, createdAt])
  @@index([userId, caseId])
}
```

REUSE the existing `InterviewReportStatus` enum (`IN_PROGRESS | PENDING | READY |
FAILED`) — do NOT declare a second, duplicate enum.

Add `scenarioReports ScenarioReport[]` to `model User` next to the existing
`interviewReports InterviewReport[]` line (~line 73).

Every column except `userId`, `caseId`, `caseName`, `backgroundSnapshot`,
`avatarsSnapshot`, `status` and the timestamps must be nullable or defaulted — there
must be zero new `NOT NULL` columns on any PRE-EXISTING table (this migration creates
one new table and adds no column to any existing table).
