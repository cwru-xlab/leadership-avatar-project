Build the student scenario CRUD API with genuine server-side ownership enforcement —
the thing that does not exist anywhere in this codebase today for cases.

Purpose: REQ-29's hard requirement is that ownership is enforced IN the route handlers,
not merely displayed and not only gated by middleware. REQ-26's minimum bar and REQ-34's
unpublish-before-delete rule are likewise server-enforced, never client-trusted.
Output: a new `/api/scenario/*` route family under `STUDENT_ROUTES`, writing to the same
S3 `cases/` prefix as admin cases.
</objective>

  <name>Task 1: Shared scenario validation module</name>
  <files>lib/scenario/validation.ts</files>
  <action>
Create `lib/scenario/validation.ts`, the single definition of REQ-26's "cannot save
without a situation, at least one character, and criteria" bar. It is imported by the
server routes in Task 2 and re-used by the builder UI in plan 09-05, so the client and
server can never disagree about what counts as complete.

Export:

```ts
export interface ScenarioInput {
  name: string;
  backgroundInfo: string;
  evaluationPrompt: string;
  avatars: CaseAvatar[];   // from @/types
  coverImage?: string;
}

export interface ScenarioFieldError { field: string; message: string; }

export function validateScenarioInput(input: unknown): {
  ok: true; value: ScenarioInput
} | {
  ok: false; errors: ScenarioFieldError[]
}
```

Rules (these are Claude's-discretion bars per CONTEXT; keep them modest and explain
each in a comment so the builder's inline hints can quote them):
- `name`: trimmed, non-empty, 3..120 chars.
- `backgroundInfo` (the situation): trimmed, non-empty, minimum 80 chars — enough that a
  one-word placeholder cannot pass, low enough that a real short scenario can. Max 20000.
- `avatars`: an array with at least ONE entry. Every entry must have a trimmed non-empty
  `name` and `role`, and a non-empty `profileId` (the existing `VideoAudioProfile` id
  the `/case-play` player already knows how to load). `additionalInfo` may be empty.
  `id` is generated client-side per character; if absent, mint one. No cap on the
  number of characters.
- `evaluationPrompt` (the criteria): trimmed, non-empty, minimum 40 chars, max 8000.

Return ALL failing fields at once (field-level errors), never a single generic message.
Trim every string in the returned `value`. Strip any property not in `ScenarioInput`
(most importantly `id`, `ownerId`, `published`, `createdBy`, `cohortIds`) — the routes
set those themselves; a client must not be able to smuggle them in.

Also export `export const SCENARIO_LIMITS` holding the numeric bounds above, so the
builder UI can render the same numbers instead of hardcoding duplicates.

<task type="auto">
  <name>Task 2: Owner-scoped /api/scenario CRUD routes</name>
  <files>app/api/scenario/add/route.ts, app/api/scenario/edit/route.ts, app/api/scenario/delete/route.ts, app/api/scenario/list/route.ts, app/api/scenario/publish/route.ts, app/api/scenario/avatars/route.ts</files>
  <action>
Create six route handlers. EVERY one begins with the exact auth preamble used by
`app/api/interview/session/start/route.ts:38-45` — read
`request.cookies.get(siteConfig.auth.cookie.name)?.value`, call
`getCurrentUser(token || "")` from `@/lib/auth`, return 401 `{error:"Unauthorized"}`
if falsy. Do not invent a new auth helper. All storage goes through `s3Storage`
(`@/lib/s3-client`) against the existing `cases/` prefix — `getCase`, `listCases`,
`saveCase`, `deleteCase`, `caseExists`. No new S3 prefix, no key-layout change.

Define a local helper in each write route (or a small shared function in
`lib/scenario/validation.ts` if cleaner):
`loadOwnedScenario(id, userId)` → `s3Storage.getCase(id)`; return null if the case
does not exist, has no `ownerId`, or `ownerId !== userId`. Callers turn null into
**404 `{error:"Scenario not found"}`** — the same body and status for "missing",
"admin-authored" and "someone else's". Never 403, never a distinguishing message.

**POST `/api/scenario/add`**
- Validate the body with `validateScenarioInput`; on failure 400 `{error, fields}`.
- Generate a collision-proof id SERVER-SIDE. Two students may name a scenario the
  same thing and the `cases/` prefix is shared with admin cases, so a bare
  name-slug id (what `lib/case-storage.ts`'s `generateId` does for admin cases)
  WILL collide. Use `scn-${slug}-${randomUUID().slice(0,8)}` where `slug` is the
  name lowercased, non-alphanumerics collapsed to `-`, trimmed, truncated to 40
  chars, and replaced with `scenario` if empty. Assert the result is not the
  literal `"new"` and re-roll on the (impossible) `caseExists` hit.
- Build the `CaseStudy`: validated fields, `ownerId: currentUser.id`,
  `published: false` (REQ-30 private by default), `cohortIds: []`,
  `createdBy`/`lastEditedBy`: `currentUser.name ?? currentUser.email`,
  `createdAt`/`lastEditedAt`: `new Date().toISOString()`.
- `s3Storage.saveCase(...)`, return 201 `{success:true, scenario}`.

**POST `/api/scenario/edit`** — body `{id, ...ScenarioInput}`.
- `loadOwnedScenario` first (404 on miss), THEN validate the input (400 on miss).
- Write back preserving `id`, `ownerId`, `published`, `cohortIds`, `createdBy`,
  `createdAt` from the existing object — these are immutable here. Update the
  validated fields plus `lastEditedBy`/`lastEditedAt`. Return `{success:true, scenario}`.

**POST `/api/scenario/publish`** — body `{id, published: boolean}`.
- `loadOwnedScenario` (404 on miss). Set `published` to the boolean, update
  `lastEditedAt`, save. Return `{success:true, published}`.
- This deliberately reuses the Phase 7 `published` flag, which gates DISCOVERY only
  and is not access control — keep that semantic, do not add an access check to
  `/api/case/get`.

**POST `/api/scenario/delete`** — body `{id}`.
- `loadOwnedScenario` (404 on miss).
- REQ-34 guard: if `existing.published === true`, return **409**
  `{error:"Unpublish this scenario before deleting it."}` and write nothing.
- Otherwise `s3Storage.deleteCase(id)` and return `{success:true}`. Do NOT touch any
  `ScenarioReport` row — reports intentionally survive (REQ-34); `caseId` is a bare
  string with no FK, so there is nothing to cascade and nothing to clean up.

**GET `/api/scenario/list`**
- `const all = await s3Storage.listCases()`.
- Return `{ success: true, mine, shared }` where
  `mine = all.filter(c => c.ownerId === currentUser.id)` (every state, published or
  not — an author always sees their own drafts) and
  `shared = all.filter(c => c.ownerId && c.ownerId !== currentUser.id && c.published === true)`.
- Admin-authored cases (no `ownerId`) appear in NEITHER array — `/case-play`'s second
  section keeps getting those from the untouched `/api/case/list?publishedOnly=true`.
- Never return another user's `ownerId` raw to the client: map `shared` rows through a
  small explicit projection that drops `ownerId` and `cohortIds` and keeps
  `{id, name, backgroundInfo, coverImage, avatars, published, createdBy, createdAt, lastEditedAt}`.
  Do NOT spread the row (same discipline as `lib/interview/report-dto.ts:53-59`).
  `mine` may keep `ownerId` since it is the caller's own id.
- Sort both arrays newest-first by `lastEditedAt`.

**GET `/api/scenario/avatars`** — the character catalog the builder's card grid reads.
- Call `s3Storage.listProfiles()` (the same source the admin `<Select>` uses via
  `/api/profile/list`), then return an EXPLICIT projection, field by field, never a
  spread: `{ id, name, description, portrait, avatarName }` only.
- Deliberately DROP `knowledgeId`, `voice`, `quality`, `language`, `createdBy`,
  `lastEditedBy` and the timestamps — `/api/profile/list` today returns the full
  `VideoAudioProfile` and is ADMIN-gated; this route exists precisely so students get
  a picker catalog without that surface. Do NOT add `/api/profile/list` to
  `STUDENT_ROUTES` and do NOT modify `app/api/profile/list/route.ts`.
- Sort by `name`. Return `{ success: true, avatars }`.
- This is what makes REQ-27 work without a data-model change: the builder shows a card
  grid of these, stores the chosen `id` into `CaseAvatar.profileId`, and the existing
  `/case-play` player's `loadAvatarConfig` (`app/case-play/[caseId]/page.tsx:370`)
  resolves it through the already-student-gated `/api/profile/get` exactly as it does
  for admin cases. Never write a LiveAvatar catalog id from
  `/api/interview/interviewers` into `profileId` — those are different id spaces and
  `/api/profile/get` would 404 (silently, via the player's catch block).

Log only ids and user ids on error paths — never scenario body text.
