  <action>
Create the page by following `app/interview/[type]/report/[reportId]/page.tsx` closely
(read it in full first) — same shell structure, same param handling for this Next
version, same polling discipline, same palette.

Fetch `GET /api/scenario/report/${reportId}` with `credentials: "include"` on mount.
Poll every ~3s while `status` is `IN_PROGRESS` or `PENDING`, stopping as soon as the
status is in `SCENARIO_REPORT_TERMINAL_STATUSES` from `lib/scenario/report-dto.ts`. Cap
the polling (e.g. stop after ~3 minutes with a "this is taking longer than expected"
message plus a manual refresh button) so the page can never spin forever. A 404 must
produce exactly ONE request, never a poll loop — the interview report page's
single-call-then-404-shell behaviour is the precedent to match.

Branches:
- **404 / not found:** a shell reading "Report not found" with a button back to
  `/case-play`. This is the SAME shell a non-owner sees — the API returns an identical
  404 for a bad id and someone else's report, and the UI must not distinguish them either.
- **IN_PROGRESS / PENDING:** the pending treatment — `<ReportScoreCards pending />` (or
  whatever prop shape that component already takes for pending) plus copy explaining the
  evaluation is running.
- **FAILED:** show `failureReason` in a readable danger card, still render the score cards
  and the scenario snapshot strip, and offer a button back to `/case-play`. Do NOT build a
  retry control — the interview side has one at `/api/interview/report/[reportId]/retry`,
  but no scenario equivalent exists and this phase does not add one; say plainly that the
  run's transcript was kept.
- **READY:** `<ReportScoreCards scores={report.scores} />` then
  `<ReportMarkdown markdown={report.reportMarkdown} />`.

Above the score cards in both READY and FAILED, render a compact **scenario snapshot
strip** from `report.scenario`: the scenario name, the character names and roles as
chips, and a "Criteria applied" presence indicator. Label the strip so its meaning is
explicit, e.g. "This scenario as it was when you practiced" — REQ-33's whole point is that
this stays truthful after the author edits or deletes it. Render the criteria only as a
presence chip or a collapsed disclosure, and NEVER render any character's hidden
`additionalInfo` (09-03's DTO already strips it; do not reintroduce it by fetching the
live case).

Navigation: a top "Back to practice" link to `/case-play` whose label and destination
agree — the exact mismatch bug found in Phase 7's walkthrough (`07-07-SUMMARY.md`), so do
not repeat it. Do not add a page-level auth check; `middleware.ts` gates `/case-play`.
