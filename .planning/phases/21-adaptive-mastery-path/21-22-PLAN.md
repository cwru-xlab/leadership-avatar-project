<objective>
Give the student a way to actually TAKE a knowledge check — and to contest the
mark they get.

21-15 can reverse a contested grade. None of it is reachable. `submitAndGrade`
has no caller outside a verifier, and 21-19's path panel links a

and "graded deterministically" are both true of a library nobody can use.

is worded as "contest from the surface that showed them the mark". That affordance
lands here, which is also where the attempt id it needs is in hand.

Output: an attempt route, a four-format card, the page a path step links to, and
a surface verifier.

  <name>Task 1: Add the attempt route — GET a keyless check, POST an answer</name>
  <files>app/api/study-plans/checks/[checkId]/attempt/route.ts</files>
  <action>
Create the route. Match the auth and response conventions of
`app/api/study-plans/[planId]/route.ts` exactly — same session accessor, same
error envelope shape, same status codes. Do not invent a new convention.

The path segment is `[checkId]`, NOT `[attemptId]`. 21-15's contest route is
`app/api/study-plans/checks/[attemptId]/contest/route.ts` and keys on the
ATTEMPT; this one keys on the CHECK, because before submission no attempt exists.
State that distinction in a block comment — the two sibling routes differing in
what their id means is the kind of thing a later reader "corrects" into a bug.

`GET` — the check as the student must see it:
1. Load the `KnowledgeCheck` with ownership in the WHERE clause (`id: checkId`
   AND the owning user). Absent or not owned → **404, not 403.** A 403 confirms
   the row exists, which leaks that another student has a check with that id.
2. Build a KEYLESS DTO. This is the load-bearing requirement of the whole plan.
   Return `format`, `competencyKey`, the per-format display payload, and
   `quotedText` with its `sourceReportId` and `turnIndex` so the student can see
   which session the quote came from. Return NOTHING else from the row.
   Specifically NEVER: `answerKey` in any form, `correctIndex`, `betterIndex`,
   `accepted`, or a `correct`/`isCorrect` flag on an option. For
   `MULTIPLE_CHOICE` and `PICK_BETTER_RESPONSE`, return options as a plain string
   array — do not return objects, because an object is where a `correct: true`
   field eventually gets added by someone being helpful.
   Build this DTO in an exported pure function `toKeylessCheckDTO(row)` so Task 4
   can assert over its output without a running server.
3. If an attempt already exists for this check and user, include it as
   `attempt: { id, score, correct, gradedBy, detail, contested: boolean }` so
   revisiting the page shows the previous mark rather than an empty form. Include
   `detail` — 21-11's `DeterministicGrade.detail` names the correct option TEXT
   after the fact, which is the only moment revealing it is correct, because the
   answer is already submitted and locked by the unique constraint.

`POST` — submit and grade:
1. Parse the body as a per-format response: `{ selectedIndex }`,
   `{ blanks: string[] }`, `{ betterIndex }`, or `{ rewrittenLine }`. Validate
   shape BEFORE calling into grading and return 400 naming the offending field —
   21-11 THROWS on an unanswerable submission (out-of-range index, wrong blank
   count) rather than marking it wrong, and a thrown error must surface as a 400,
   not a 500. Map 21-11's validation throws to 400 explicitly.
2. Call `submitAndGrade({ userId, knowledgeCheckId: checkId, response })`. Pass
   no `callModel` — the real model path is wanted here; the injectable stub exists
   for 21-11's battery.
3. Catch `AlreadyAnsweredError` → **409** with the existing attempt's mark, so the
   client can render the previous result instead of an error. A double-click must
   not look like a failure.
4. On success return **201** with `{ attempt: { id, score, correct, gradedBy,
   detail, rationale? } }` and nothing else. `attempt.id` is REQUIRED in the
   response: it is what the contest control in Task 2 POSTs to 21-15's route, and
   without it REQ-112's affordance has nothing to send.
5. `maxDuration`: raise it only for the rewrite format's model call — set 30.
   Do not set 60; a single grading call is not a generation batch.
6. Do NOT mark the path step complete here. Step completion belongs to
   `markStepComplete` (21-08) and the path route; a second writer would let a
   step complete without the path's own invariants being re-checked. Note the
   omission as deliberate and record in the SUMMARY where step completion
   actually happens for a check step.

  <files>components/study-plan/KnowledgeCheckCard.tsx</files>
  <action>
Create `components/study-plan/KnowledgeCheckCard.tsx`, a client component
following `app/reports/page.tsx`'s existing Tailwind idiom. One component, four
format branches — not four components, because the submit/mark/contest shell is
identical and duplicating it three times is how three of them drift.

Props: the keyless DTO from Task 1, plus `planId` and `checkId`.

1. QUOTE BLOCK, when `quotedText` is present. Render the quote VERBATIM in a
   visually distinct block, labelled as the student's own words from a named
   session, with the session date and a link to that report. Do NOT trim,
   ellipsize, re-case, or collapse whitespace in the quote on the way to the
   screen — 21-04's verbatim gate guarantees the stored text matches the
   transcript, and cosmetic client-side tidying would break the guarantee at the
   last possible moment, where no verifier is watching. Render it inside a
   `<blockquote>` with `white-space: pre-wrap`. Comment the reasoning.

2. FORMAT BRANCHES:
   - `MULTIPLE_CHOICE` — four radio inputs in a `<fieldset>` with a `<legend>`
     carrying the prompt. Submit `{ selectedIndex }`.
   - `PICK_BETTER_RESPONSE` — two radio inputs over the two candidates, plus the
     `rationalePrompt` text when non-null. Submit `{ betterIndex }`. Do NOT label
     either candidate as "yours" even when one is the student's own line: naming
     it is a tell that gives the answer away for free.
   - `FILL_IN_BLANK` — interleave `segments` and `blankCount` text inputs so the
     sentence reads as a sentence with gaps, each input labelled "blank N" for
     screen readers. Submit `{ blanks: string[] }` with exactly `blankCount`
     entries, in order, untrimmed — 21-11 owns normalization and does it
     deliberately; trimming in the client would mean the grader's documented
     policy is not the policy actually applied.
   - `REWRITE_WEAK_LINE` — the `weakLine` shown as the student's own line, the
     `techniqueHint` shown as the skill to apply, the `rubricCriteria` listed as
     what the rewrite will be judged on, and a textarea. Submit
     `{ rewrittenLine }`. Show the criteria BEFORE submission, not after: a
     student graded against hidden criteria cannot learn from the grade.

3. SUBMIT AND MARK. Disable submit while in flight and when an attempt already
   exists. On 201, render the mark: correct/incorrect, the score, 21-11's
   `detail`, and for a rewrite the model's `rationale`. On 409, render the
   returned prior mark with a line saying this check was already answered. On
   400, show the field-level message. Never show a raw error body.

4. CONTEST AFFORDANCE (REQ-112). Visible ONLY after a mark exists, since there is
   nothing to contest before. A "This grading looks wrong" control that opens a
   short reason textarea and POSTs to
   `/api/study-plans/checks/{attempt.id}/contest` — note that path keys on the
   ATTEMPT id from the submission response, not the check id. On success, replace
   the control with a confirmation stating plainly that the contribution to
   mastery has been reversed pending review, because that is what 21-15 actually
   does and a student who is not told will think nothing happened. On a 409
   (already contested) show the same confirmation rather than an error.
   Do NOT re-grade, re-submit, or clear the displayed mark on contest. The mark
   stands; the contest is a flag.

5. NO ANSWER REVEAL BEFORE SUBMISSION. Nothing in this component may compute,
   infer, or display correctness before a response comes back from the server.
   Add a comment saying so. The three closed formats are graded server-side
   specifically so the browser never holds the key.

Accessibility: every input labelled; radios grouped in a `fieldset`/`legend`;
correctness conveyed in TEXT as well as colour; the mark region `aria-live`
polite so a screen reader announces it on arrival.
  </action>
