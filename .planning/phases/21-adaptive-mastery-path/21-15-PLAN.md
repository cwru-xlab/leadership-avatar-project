<objective>
Let the student contest a grading, reverse the disputed contribution immediately,
and flag the question behind it.

Purpose: 21-CONTEXT.md names this as one of the two guardrails that matter most —
"a way to flag a wrong mark, which also surfaces bad generated questions instead
of letting them quietly damage mastery." The second clause is the real design
requirement. A contest system that only records complaints is a feedback form.
This one has to do two things the student cannot see: stop the mark counting, and
raise the question for review so it stops being served.

The reason immediate reversal is correct rather than reversal-on-review: these
questions are MODEL-GENERATED from the student's own transcript. A wrong mark is
a plausible failure, not a rare one, and leaving it in the figure until a human
reviews it means the mastery number is knowingly wrong for the whole review
window. Reversal is recorded, not destructive (21-05's ledger keeps the row), so
resolving the contest as REJECTED can restore it.

Output: `lib/study-plan/checks/contest.ts`, a POST route, and a battery.
</objective>

  <files>lib/study-plan/checks/contest.ts</files>
  <action>
Create `lib/study-plan/checks/contest.ts`.

Export `CONTEST_STATUSES = ["OPEN", "UPHELD", "REJECTED"] as const`.

`raiseContest(args: { userId: string; attemptId: string; reason: string }):
Promise<{ contestId: string; contributionsReversed: number; checkFlagged: boolean }>`

In ONE `prisma.$transaction`, in this order:
1. Load the attempt joined to its `KnowledgeCheck`, scoped by `userId` in the
   WHERE clause. Throw `NotFoundError` if absent — do NOT distinguish "does not
   exist" from "belongs to someone else" in the error message, so the endpoint
   cannot be used to probe for other users' attempt ids.
2. Require the attempt to be GRADED (`gradedAt` non-null). Contesting an ungraded
   attempt is meaningless and would reverse nothing while looking like it worked.
3. Validate `reason`: 10..2000 characters after trim. The 10-character floor is
   deliberate — a one-word contest gives a reviewer nothing, and the student is
   the only source of why the mark is wrong.
4. Create the `GradingContest` with `status: "OPEN"`.
   `attemptId` is `@unique` (21-03), so a second contest throws P2002 — catch it
   and rethrow `AlreadyContestedError` carrying the existing contest id, so the
   UI can show the existing contest instead of a database error.
5. REVERSE. Find every `MasteryContribution` with `sourceAttemptId = attemptId`
   and a null `reversedAt`, and call `reverseContribution` on each with reason
   `"contested:<contestId>"`. 21-11 writes exactly one, but query and reverse ALL
   of them rather than assuming the count — if a future refactor ever writes two,
   reversing one would leave half a disputed mark in the figure, which is worse
   than either extreme. Return the count so the battery can assert it.
6. FLAG THE QUESTION. Set `KnowledgeCheck.flaggedAt` and `flagReason` to
   `"contested:<contestId>"` if not already flagged. Do NOT overwrite an existing
   flag — the first contest is the one that discovered the problem, and its
   reference should survive. Return whether a flag was newly set.

Everything in one transaction: a contest recorded without its reversal leaves the
disputed mark counting, which is the exact failure 21-CONTEXT.md's "instead of
letting them quietly damage mastery" names.

`resolveContest(args: { contestId: string; status: "UPHELD" | "REJECTED";
resolutionNote: string }): Promise<void>`
- Throws if the contest is not `OPEN`.
- `UPHELD` → the contribution stays reversed, permanently. Also append to the
  `KnowledgeCheck`'s `flagReason` that the contest was upheld, so
  `listFlaggedChecks` can distinguish a confirmed-bad question from a merely
  disputed one.
- `REJECTED` → the mark stood. Write a NEW `MasteryContribution` restoring the
  original score rather than clearing the original row's `reversedAt`. 21-05's
  ledger is append-only apart from the two reversal columns, and un-reversing
  would erase the fact that a dispute happened. Carry the original
  `occurredAt` so the restored contribution lands in the window it belongs to,
  and record its reason. State this reasoning in a comment — un-reversing is the
  obvious implementation and the wrong one.
- Note that nothing in this plan exposes `resolveContest` through a route. There
  is no admin review UI in this phase and deliberately so; it is reachable from a
  script. Say that explicitly so a reader does not assume the route is missing by
  accident.

`listFlaggedChecks(opts?: { minContests?: number }): Promise<Array<{ checkId;
format; competencyKey; flagReason; contestCount; generationModel }>>`
- Every `KnowledgeCheck` with a non-null `flaggedAt`, with its contest count.
- This is the "surfaces bad generated questions" half. Ordered by contest count
  descending: a question several students contested is a generation-prompt
  problem, not a one-off.

`POST` accepts `{ reason: string }`, reads `attemptId` from the route params, and
calls `raiseContest({ userId: currentUser.id, attemptId, reason })`.

Responses:
- 201 with `{ contestId, contributionsReversed, checkFlagged }`.
- 400 on a reason failing validation, with the validation message.
- 404 on `NotFoundError` — the same status whether the attempt does not exist or
  belongs to another user. Comment why: distinguishing them turns the endpoint
  into an id oracle.
- 409 on `AlreadyContestedError`, with the existing contest id so the client can
  show it.
- 500 with a generic message on anything else, and `console.error` the real one.
  Never return a Prisma error body — the existing routes do not and a database
  error string can carry column and constraint names.

Do NOT add a GET, a DELETE, or a resolution endpoint. A student withdrawing a
contest would need the reversal reconsidered, and that decision has not been
made; leaving it out is better than guessing. Note that in a comment.

Place the route at `app/api/study-plans/checks/[attemptId]/contest/` — NOT under
`[planId]`. The attempt id is globally unique and already resolves ownership
through its own join, so nesting under a plan id would add a second identifier
that could disagree with the first. State that choice in a comment.

graded attempt via `submitAndGrade` (21-11), and confirm one
`MasteryContribution` exists.

Assert:
1. BASELINE. `computeMastery` over `readContributions(user)` gives a non-null
   figure for the check's competency. Record it.
2. REVERSAL IS IMMEDIATE. `raiseContest` → `contributionsReversed === 1`, the
   contribution row's `reversedAt` is non-null with reason containing the contest
   id, and `readContributions(user)` (default `includeReversed: false`) NO LONGER
   returns it. Then recompute mastery and assert the competency's figure CHANGED
   from the baseline. This is the assertion that proves the mark stopped counting
   — asserting the column alone would pass even if the computation path ignored
   it.
3. THE ROW SURVIVES. `readContributions(user, { includeReversed: true })` still
   returns it. Nothing was deleted.
4. QUESTION FLAGGED. The `KnowledgeCheck.flaggedAt` is non-null and
   `listFlaggedChecks()` includes it with `contestCount: 1`.
5. IDEMPOTENCE. A second `raiseContest` on the same attempt throws
   `AlreadyContestedError` carrying the first contest id, and `contributionsReversed`
   did not increase — assert by re-querying the reversed count, not by trusting
   the throw.
6. OWNERSHIP. `raiseContest` with a different `userId` throws, and the error
   message contains neither the attempt id nor either user id.
7. UNGRADED. Create an attempt with `gradedAt: null` and assert `raiseContest`
   throws and wrote nothing — no contest row, no reversal, no flag. Check all
   three, since a partial write here is the transaction failure mode.
8. REASON VALIDATION. A 3-character reason throws; a 2,500-character reason
   throws; a 50-character reason succeeds.
9. RESOLVE UPHELD. Resolve as `UPHELD` → the contribution stays reversed, mastery
   stays at the post-contest figure, and the flag reason records the upholding.
10. RESOLVE REJECTED. On a SECOND attempt/contest pair, resolve as `REJECTED` →
    a NEW contribution exists (total row count for that attempt is now 2), the
    ORIGINAL row's `reversedAt` is STILL non-null, the new row's `occurredAt`
    equals the original's, and the recomputed mastery figure returns to the
    baseline. All four, because the append-not-unreverse choice is exactly the one
    a later refactor would simplify away.
11. DOUBLE RESOLVE. Resolving an already-resolved contest throws.
12. FLAG RANKING. Create a second contest against a DIFFERENT attempt of the same
    check by a second scratch user, and assert `listFlaggedChecks` reports
    `contestCount: 2` and orders it above a single-contest check.

Clean up every scratch row in a `finally`.
