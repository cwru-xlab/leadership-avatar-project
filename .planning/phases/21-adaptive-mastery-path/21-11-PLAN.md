Grade the four formats: the three closed ones deterministically, the rewrite with
a model at the lower weight.

Purpose: 21-CONTEXT.md locks that all formats move mastery but model-graded
rewrites count for LESS than the deterministically-graded formats. 21-05 declared
the weights and 21-06 declared which format is in which class. This plan is where
the split becomes behaviour: a multiple-choice answer must never reach a model,
and a rewrite's grade must never be recorded at the deterministic weight.

grader quietly starts marking correct answers wrong, which is precisely the
failure REQ-112's contest mechanism exists to catch. Better to not create it.

  <behavior>
`gradeDeterministic(format, payload, answerKey, response): DeterministicGrade`
where `DeterministicGrade = { correct: boolean; score: number; detail: string }`,
`score` being 0 or 1 for MULTIPLE_CHOICE and PICK_BETTER_RESPONSE, and
`blanksCorrect / blankCount` for FILL_IN_BLANK so partial credit exists for a
multi-blank item. Throws if called with `REWRITE_WEAK_LINE` — the type system
should prevent it, and the throw catches the `as any` that eventually appears.

MULTIPLE_CHOICE cases:
- `{ selectedIndex: 2 }` vs `correctIndex: 2` → correct, score 1.
- wrong index → incorrect, score 0, `detail` naming the correct option TEXT (not
  just its index), so the student learns something from the mark.
- `selectedIndex: 4` out of range, negative, non-integer, or missing → THROW,
  not "incorrect". An unanswerable submission is a client bug; marking it wrong
  would damage mastery for a bug the student did not cause.

PICK_BETTER_RESPONSE: same shape on `betterIndex`, 0 or 1 only.

FILL_IN_BLANK cases — the normalization policy here is DIFFERENT from
`verbatim.ts`'s and that difference is deliberate, so state it in a block comment
referencing the other file. Verbatim matching protects the student's words from
being altered; blank matching accepts a student's typing. Permitted here:
NFC, trim each blank, collapse internal whitespace runs to one space, and
case-INSENSITIVE comparison. Not permitted: stemming, fuzzy distance,
punctuation stripping, or substring matching — each would silently accept a wrong
answer, and the student would learn the wrong thing.
- Exact match per blank → correct.
- Match against the second entry in a blank's `accepted` array → correct
  (synonyms work).
- `"  Active   Listening "` against `accepted: [["active listening"]]` → correct,
  proving trim, collapse, and case-folding together.
- One of two blanks right → score 0.5, `correct: false`. Partial credit without
  calling it correct.
- A response with fewer entries than `blankCount`, or more → THROW.
- `accepted` containing an empty string → THROW at grade time as well as at
  validation time (21-06), because an empty accepted answer matches an empty
  submission and marks a blank answer correct.

`gradeRewriteWithModel(args: { payload: RewriteWeakLinePayload; response:
{ rewrittenLine: string }; callModel?: ... }): Promise<{ score: number;
rationale: string; model: string } | { ok: false; reason: string }>`
- `REWRITE_GRADING_SCHEMA`: `strict: true`, asking for one `score` integer 1..5
  and one `rationale` string, plus a per-criterion boolean array matching
  `payload.rubricCriteria.length`. Normalize score to 0..1 via
  `normalizeRubricScore` from `lib/mastery/weights.ts` (21-05, already a
  dependency of this plan) — import it, do NOT restate `(score - 1) / 4`. One
  normalizer, because a session dimension scoring 1 and a rewrite scoring 1 must
  both contribute 0, and two copies of the formula will eventually disagree about
  the floor. 21-21's mapper imports the same function, which is what keeps check
  grades and session scores on one scale. The conversion makes a floor-scoring
  rewrite contribute 0 rather than 0.2 — the 1-5 rubric scale
  this project uses elsewhere has 1 as its floor, not as 20% credit.
- Reject a returned criterion array whose length does not match; a grader that
  invented criteria graded a different question.
- Clamp nothing silently: an out-of-range score is a failure, not a clamp.
- Injectable `callModel`, same pattern as 21-10, so the battery needs no API key.

`submitAndGrade(args: { userId; knowledgeCheckId; response; callModel? }):
Promise<GradeOutcome>`
- Loads the check, verifies `userId` owns it (scoped WHERE, not post-filter).
- Rejects a second submission for the same check — 21-03's
  `@@unique([knowledgeCheckId, userId])` enforces it; catch P2002 and return a
  named `AlreadyAnsweredError` rather than a raw database error.
- Routes on `isDeterministicFormat(check.format)`. Writes the attempt with
  `gradedBy: "DETERMINISTIC"` and `graderModel: null`, or `gradedBy: "MODEL"`
  with the model name and rationale.
- Writes exactly ONE `MasteryContribution` via `recordContributions`, with
  `source: CONTRIBUTION_SOURCE_FOR_FORMAT(check.format)`,
  `competencyKey: check.competencyKey`, `rawScore` = the normalized score,
  `occurredAt` = the submission time, and `sourceAttemptId` = the new attempt id.
  One contribution per attempt — asserting that count is how a later refactor
  that double-records gets caught.
- Attempt write and contribution write go in ONE transaction. A graded attempt
  with no contribution is invisible mastery; a contribution with no attempt
  cannot be contested.
  </behavior>
