Export `LEVEL_THRESHOLDS: ReadonlyArray<{ level: Level; minPercent: number;
name: string }>` with `minPercent` at `0, 40, 55, 70, 85`. Mark all five
**PROVISIONAL UNTIL CALIBRATED** with their derivation, following the Phase 20
convention: the underlying rubric is a 1-5 integer scale normalized by
`(score - 1) / 4`, so a straight-3s performance is 50% and a straight-4s is 75%.
The bands are placed so that a consistent 3 lands at level 2 (Building — honest,
not punishing), a consistent 4 at level 4 (Strong), and level 5 requires better

distributions.

Export `levelFor(args: { percent: number | null; tier: EvidenceTier }): {
level: Level | null; name: string; provisional: boolean; nextLevelAtPercent:
number | null }`:
- `percent === null` → `{ level: null, name: "Not yet measured", provisional:
  false, nextLevelAtPercent: null }`. A null figure has no level. Do NOT return
  level 1 — level 1 means measured and starting out, and conflating the two tells
  a student they are at the bottom of something they have never attempted.
- `tier === "THIN"` → the level is computed normally but `provisional: true`. A
  level is a stronger claim than a percentage; asserting level 4 on two sessions
  would be exactly the "presented as if well-evidenced" failure REQ-105 forbids,
  and withholding it would be the "withheld" failure. Flagging it is the same
  resolution 21-13 chose, applied consistently.
- `nextLevelAtPercent` is the next threshold's `minPercent`, or null at level 5.
  This is the "progression" half of REQ-119 — a level with no visible next target
  is a badge, not progression.
- Thresholds are INCLUSIVE lower bounds: exactly 40% is level 2. Assert both
  sides in the battery.
- Throw on a percent outside 0..100 rather than clamping.

Add a comment stating what deliberately does NOT exist in this module: no level
is a prerequisite for anything, no level grants access to anything, and no
function takes a "current level" to decide what is available. Naming the absence
is what makes a later addition visibly a change in policy rather than a feature.

<task type="auto">
  <name>Task 2: Daily and weekly goals computed from the ledger</name>
  <files>lib/study-plan/goals.ts</files>
  <action>
Create `lib/study-plan/goals.ts`.

Export `GOAL_DEFAULTS = { dailyActivities: 1, weeklyActivities: 4 } as const`,
marked **PROVISIONAL UNTIL CALIBRATED**. Record the derivation: one activity a
day is achievable alongside coursework and is the smallest unit that still means
something; four a week is deliberately LESS than seven, so a student who misses
days can still hit the weekly goal. That asymmetry is intentional and is the
closest this phase gets to the motivational function a streak would serve —
without the punishment a streak carries. Say that explicitly, since it is the
design answer to "why no streaks."

```ts
export interface GoalProgress {
  daily:  { target: number; completed: number; met: boolean; windowStart: string; windowEnd: string };
  weekly: { target: number; completed: number; met: boolean; windowStart: string; windowEnd: string };
}

export function goalProgress(args: {
  contributions: ReadonlyArray<MasteryContributionRow>;
  now: Date;
  timeZone: string;
  targets?: { dailyActivities?: number; weeklyActivities?: number };
}): GoalProgress
```

- `now` and `timeZone` are REQUIRED parameters. A "today" computed from the server
  clock in UTC tells a student at 8pm Eastern that their evening session counted
  toward tomorrow. Use `Intl.DateTimeFormat` with the supplied zone to find the
  local day boundary; do not add a date library. State the reasoning.
- An "activity" is ONE contribution. Count DISTINCT contributions in the window
  — but count a single session's multiple per-competency contributions (which
  21-16 writes, one per competency) as ONE activity. Group by
  `sourceReportId ?? sourceAttemptId` and count distinct groups. Without this, one
  coached session would satisfy a weekly goal of four on its own, and the goal
  would measure nothing. This is the subtlest correctness issue in the plan;
  assert it directly.
- Windows: daily = local midnight today to `now`. Weekly = local midnight of the
  current ISO week's Monday to `now`. Declare the Monday choice rather than
  leaving it to locale, so the week boundary is stable for every student.
- Reversed contributions: the caller passes `readContributions`'s default
  (reversed excluded), so a contested item stops counting toward a goal too. Add a
  comment noting that this is the consistent choice and that it is the caller's
  responsibility, matching 21-09's single-filter-location rule.
- `met` is `completed >= target`. No partial credit, no overachievement bonus.
- `targets` override lets a student's preference apply later; this phase ships the
  defaults and does not persist a per-student target. Note that as a deliberate
  omission, not an oversight.

Add a comment listing what this module deliberately does NOT compute: consecutive
days, longest run, "don't break your chain", any day-over-day comparison, and any
notion of a day being missed. A streak is exactly "consecutive days met", so the
guard in Task 3 looks for precisely that.
  </action>
  <verify>`npx tsc --noEmit` clean. `grep -ci 'streak\|consecutive\|chain' lib/study-plan/goals.ts` finds matches ONLY inside the does-not-compute comment. `grep -c 'new Date()' lib/study-plan/goals.ts` returns 0.</verify>
  <done>Defaults declared and marked provisional with the no-streaks design reasoning; now and timeZone are required; activities are distinct sessions not contributions; the ISO-Monday week boundary is declared; reversed items excluded via the caller; and the non-computed streak concepts are listed by name.</done>
</task>
