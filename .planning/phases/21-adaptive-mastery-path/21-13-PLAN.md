<objective>
Attach evidence thinness to every mastery figure at the single server exit, so a
thin figure is shown WITH its thinness rather than withheld or disguised.

Purpose: 21-CONTEXT.md is specific and the specificity matters — "A competency
backed by two sessions still displays, with an explicit indication of how little
evidence sits behind it. Do not silently present a thin number as if it were
well-evidenced." Both failure modes are named: hiding it, and showing it bare.
The precedents cited are Phase 10's coverage handling (`visualUnscoredReason` /
`vocalUnscoredReason` carry WHY a thing is unscored rather than coercing to a
value) and Phase 12's thin visual-data handling.

The structural lesson from 20-06 applies: the sanitizer had to run inside
`toReportDto` — the single server exit — because narrowing in the browser would
already have shipped the unsafe value. Thinness is the same shape of problem. If
the tier is computed in a component, a second component will forget, and the bare
number ships.

Output: `lib/mastery/thinness.ts`, `lib/mastery/mastery-dto.ts`, and a boundary
battery.
</objective>

  <name>Task 1: Declare the evidence tiers and the threshold</name>
  <files>lib/mastery/thinness.ts</files>
  <action>
Create `lib/mastery/thinness.ts`.

Export `EVIDENCE_TIERS = ["NONE", "THIN", "EMERGING", "ESTABLISHED"] as const` and
`type EvidenceTier`.

Export `THINNESS_THRESHOLDS`:
```ts
export const THINNESS_THRESHOLDS = {
  /** Below this weighted sum, the figure is THIN. */
  thinBelowWeightSum: 2.0,
  /** At or above this weighted sum, the figure is ESTABLISHED. */
  establishedAtWeightSum: 6.0,
} as const;
```

Tier on `weightSum`, NOT on raw contribution count. This is the discretion call
and it needs its reasoning recorded: a count-based threshold would treat four
model-graded rewrites (4 × 0.20 = 0.8 of weighted evidence) as equal to four live
sessions (4 × 1.00 = 4.0), and the whole point of 21-05's weight table is that
those are not equal evidence. Weighting the threshold by the same weights that
compute the figure keeps one notion of evidence in the system instead of two.
State that in a block comment.

Mark both numbers **PROVISIONAL UNTIL CALIBRATED** with their derivation: 2.0
weight-sum is roughly two unaided sessions, which is the exact example
21-CONTEXT.md uses for "still displays, with thinness flagged"; 6.0 is roughly
six unaided sessions, the point at which a weighted mean stops swinging
materially on one more data point. Record that neither has been validated against
real student data, following the Phase 20 convention for provisional numbers.

Export `evidenceTierFor(args: { evidenceCount: number; weightSum: number }):
EvidenceTier`:
- `evidenceCount === 0` → `NONE`. Checked FIRST and on count, not weight — a zero
  weight sum with a non-zero count would mean a weight-table bug, and conflating
  it with "no evidence" would hide the bug.
- `weightSum < thinBelowWeightSum` → `THIN`
- `weightSum >= establishedAtWeightSum` → `ESTABLISHED`
- otherwise `EMERGING`
Throw on a negative count or weight sum rather than clamping.

Export a `TIER_DISCLOSURE: Record<EvidenceTier, { label: string; disclosure:
string | null }>` giving the words the UI must show. `NONE` →
`{ label: "Not yet measured", disclosure: "No scored sessions or checks for this
competency yet." }`; `THIN` → a disclosure naming the actual evidence behind it;
`EMERGING` → a lighter disclosure; `ESTABLISHED` → `disclosure: null`. Putting
the copy here, keyed by tier, means a component cannot render a figure without
having the matching disclosure string in hand — which is the mechanical half of
"never presented as if well-evidenced."
  </action>
  <verify>`npx tsc --noEmit` clean. `npx tsx -e "import {evidenceTierFor} from './lib/mastery/thinness'; console.log(evidenceTierFor({evidenceCount:0,weightSum:0}), evidenceTierFor({evidenceCount:2,weightSum:2.0}), evidenceTierFor({evidenceCount:9,weightSum:6.0}))"` prints `NONE EMERGING ESTABLISHED`. `grep -c 'PROVISIONAL UNTIL CALIBRATED' lib/mastery/thinness.ts` returns at least 1.</verify>
  <done>Four tiers, thresholds on weightSum with the count-vs-weight reasoning recorded, NONE decided on count first, negatives throw, both numbers marked provisional with derivation, and per-tier disclosure copy co-located with the tier.</done>

```ts
export interface CompetencyMasteryDTO {
  competencyKey: string;
  label: string;
  description: string;
  order: number;
  lifetime: { percent: number | null; evidenceCount: number; tier: EvidenceTier; disclosure: string | null; tierLabel: string };
  current:  { percent: number | null; evidenceCount: number; tier: EvidenceTier; disclosure: string | null; tierLabel: string };
  lastContributionAt: string | null;   // ISO
}

export interface MasteryDTO {
  competencies: CompetencyMasteryDTO[];
  overall: { lifetimePercent: number | null; currentPercent: number | null };
  window: { days: number; startsAt: string };
  /** Non-zero means the catalog and the ledger disagree — surfaced, not swallowed. */
  unmappedRowCount: number;
}
```

`toMasteryDTO(result: MasteryResult): MasteryDTO`:
- Emits a `lifetime` AND a `current` block for EVERY competency, each with its
  own independently-computed tier. The two must be separate: a competency with
  nine lifetime sessions and one this month is ESTABLISHED lifetime and THIN
  current, and collapsing them to one tier is exactly how a stale figure gets
  presented as current form.
- Pulls `label`, `description` and `order` from `COMPETENCIES` so the client never
  receives a bare key it has to map. A client-side key→label map is a second
  catalog, and it breaks the replaceability seam REQ-103 established.
- Sorts by `order`.
- Converts dates to ISO strings. No `Date` objects cross the boundary.
- Attaches `tierLabel` and `disclosure` from `TIER_DISCLOSURE`. There is no
  variant of this function that omits them and no optional flag to skip them.
  Write a comment: a `{ includeTiers: false }` option would be the single change
  that reintroduces the bare-number failure, so it deliberately does not exist.
- Does NOT round, re-scale, or clamp a percent. 21-09 rounded once; rounding again
  here would make two call sites disagree on the last digit.

Add a block comment naming this as the SINGLE server exit for mastery, citing
20-06's finding that a guarantee applied at render time has already shipped the
unsafe value in the page payload. Every route and every server component must go
through this function; nothing may serialize a `MasteryResult` directly.
  </action>
  <verify>`npx tsc --noEmit` clean. `grep -c 'includeTiers\|skipTier\|raw' lib/mastery/mastery-dto.ts` returns 0. `grep -c 'Math.round' lib/mastery/mastery-dto.ts` returns 0.</verify>
  <done>Every competency emits independent lifetime and current blocks, each carrying tier, tierLabel and disclosure; labels come from the catalog; dates are ISO; there is no tier-omitting variant; and the single-exit rationale is documented with its 20-06 precedent.</done>

Section 1 — TIER BOUNDARIES, asserted on both sides of each edge:
- count 0, weight 0 → `NONE`
- count 1, weight 0.20 (one model-graded rewrite) → `THIN`
- count 2, weight 1.999 → `THIN`; weight 2.0 → `EMERGING`. Both sides of the
  threshold, so the inclusive/exclusive choice is pinned rather than incidental.
- weight 5.999 → `EMERGING`; weight 6.0 → `ESTABLISHED`
- count 0 with weight 3.0 → `NONE`, proving the count-first rule
- negative count and negative weight → throw

Section 2 — THE 21-CONTEXT CASE, named as such in the check label: a competency
with exactly two live sessions (count 2, weight 2.0). Assert `percent` is
NON-NULL (it displays — nothing is withheld) and that its tier carries a non-null
`disclosure`. This is the literal scenario 21-CONTEXT.md describes, and it should
be a labelled check so the next reader can find it.

Section 3 — NO FIGURE WITHOUT A TIER. For a `MasteryResult` covering every
competency with a mixture of none/thin/established evidence, assert:
- `dto.competencies.length === COMPETENCIES.length` — no competency is dropped
  for being thin. Dropping is the "withheld" failure.
- EVERY competency has a non-empty `lifetime.tierLabel` and a non-empty
  `current.tierLabel`.
- Every competency whose `lifetime.percent` is non-null AND whose tier is `THIN`
  has a non-null `lifetime.disclosure`. A thin figure with no disclosure is the
  "presented as well-evidenced" failure, and this is the assertion that catches it.
- A competency with `percent: null` has tier `NONE` and its disclosure is also
  non-null — "not yet measured" must say so rather than render blank.

Section 4 — LIFETIME AND CURRENT TIER INDEPENDENCE. Build a competency with
lifetime count 9 / weight 9.0 and current count 1 / weight 0.2. Assert
`lifetime.tier === "ESTABLISHED"` and `current.tier === "THIN"` on the SAME
competency. This is the case that proves the two tiers are computed separately.

Section 5 — SHAPE GUARD. Assert no value in the serialized DTO is a `Date`
instance (JSON round-trip the DTO and deep-compare). Assert `unmappedRowCount` is
present even when zero — an omitted-when-zero field is a field consumers forget
to check.
