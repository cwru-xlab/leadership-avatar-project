Create the single mastery contribution ledger and the declared weight table that
feeds it, with the weight ORDERING enforced mechanically.

mastery, that model-graded rewrites count for LESS than deterministically-graded
formats, and that coached sessions count BELOW unaided practice. It explicitly

someone can edit is not a locked ordering; a constraint list a verifier checks
is. This plan builds both.

`type ContributionSource = (typeof CONTRIBUTION_SOURCES)[number]`. These are the
same four strings `MasteryContribution.source` accepts — import nothing from
Prisma for them; this module is the vocabulary's home and the schema comment in
21-03 already says the column is code-enforced.

Export `CONTRIBUTION_WEIGHTS: Record<ContributionSource, number>`:

```
LIVE_SESSION:        1.00
CHECK_DETERMINISTIC: 0.45
COACHED_SESSION:     0.40
CHECK_MODEL_GRADED:  0.20
```

These numbers are DISCRETION, the ordering is NOT. Write a block comment stating
exactly that, naming 21-CONTEXT.md, and marking all four numbers **PROVISIONAL
UNTIL CALIBRATED** with the reasoning behind each — the house convention Phase 20
set for provisional numbers. The reasoning to record: a full unaided live session
is the only unassisted evidence and anchors at 1.00; a deterministically-graded
check is real but narrow recall, under half a session; a coached session is a
whole session but scaffolded, so it sits just below the check rather than near a
live session, because the scaffolding is what the student is being tested
without; a model-graded rewrite is the weakest evidence because its grade is
itself a judgement, so it earns the floor.

Export the ordering as DATA, not prose:

```ts
export const WEIGHT_ORDERING_CONSTRAINTS: ReadonlyArray<{
  greater: ContributionSource;
  lesser: ContributionSource;
  locked_by: string;   // the 21-CONTEXT.md decision sentence
}> = [
  { greater: "CHECK_DETERMINISTIC", lesser: "CHECK_MODEL_GRADED",
    locked_by: "all formats move mastery, but model-graded rewrites count for less than the deterministically-graded formats" },
  { greater: "LIVE_SESSION", lesser: "COACHED_SESSION",
    locked_by: "coached sessions DO move mastery, weighted below unaided practice" },
];
```

Export `weightForSource(source: ContributionSource): number` which throws on an
unknown source rather than defaulting to 0 or 1 — a silent default would let a
new source either count for nothing or count as a full live session, and both are
wrong in a way nobody would notice.

Also export `MASTERY_WINDOW_DAYS = 30` and
`MASTERY_SCALE = { min: 0, max: 1 } as const`, used by 21-09's computation. They
live here so every number this phase introduces is in one calibration-reviewable
file.

Finally export the ONE scale conversion the whole phase shares:

```ts
/**
 * The project's rubric scale is 1-5 with 1 as the FLOOR, not as 20% credit.
 * So a 1 contributes 0 and a 5 contributes 1. Throws outside 1..5 or on a
 * non-finite input rather than clamping — a clamp would turn a bug into a
 * plausible-looking score.

 * consumer needs a dependency on another consumer.
 */
export function normalizeRubricScore(score: number): number
```

  <files>lib/mastery/ledger.ts</files>
  <action>
Create `lib/mastery/ledger.ts`.

```ts
export interface ContributionInput {
  userId: string;
  competencyKey: CompetencyKey;
  source: ContributionSource;
  /** Normalized 0..1. Caller converts a 1-5 rubric score; this module rejects out-of-range. */
  rawScore: number;
  occurredAt: Date;
  sourceReportId?: string | null;
  sourceAttemptId?: string | null;
}
```

`recordContributions(inputs: ContributionInput[]): Promise<number>`
- Validates every input BEFORE any write: `rawScore` in [0,1] inclusive,
  `competencyKey` present in `COMPETENCIES` (import from
  `lib/mastery/competencies.ts`), `source` in `CONTRIBUTION_SOURCES`,
  `occurredAt` not in the future. Throws naming the offending index. Validate the
  whole batch first so a partial write cannot happen — a half-recorded session
  produces a mastery figure nobody can explain.
- Snapshots `weight: weightForSource(input.source)` into each row. Do NOT store a
  source-only reference and look the weight up at read time; 21-03's schema
  comment and REQ-107 both require the snapshot, because retuning a weight must
  not retroactively rewrite a figure the student already saw.
- One `prisma.masteryContribution.createMany`. Returns the count written.

`reverseContribution(contributionId: string, reason: string): Promise<void>`
- Sets `reversedAt` and `reversedReason`. Throws if the row is already reversed —
  a double reversal would be a second, silent correction.
- NEVER deletes. Add a block comment: the ledger is append-only apart from these
  two columns, which is what lets REQ-112's contest be audited.

`readContributions(userId: string, opts?: { competencyKey?: CompetencyKey;
since?: Date; includeReversed?: boolean }): Promise<MasteryContributionRow[]>`
- Default `includeReversed: false`. Every arithmetic caller wants live
  contributions only; making that the default means a caller cannot accidentally
  include reversed rows in a figure.
- Orders by `occurredAt` ascending. Windowing filters on `occurredAt`, NEVER
  `createdAt` — a session recorded late must still land in the window it happened
  in.
- Export the row type as a narrow interface rather than re-exporting the Prisma
  model, so 21-09's pure computation can be tested with plain object literals and
  no database.

  <done>recordContributions validates the whole batch before writing and snapshots the weight; reverseContribution marks rather than deletes and rejects a double reversal; readContributions excludes reversed rows by default and windows on occurredAt.</done>
