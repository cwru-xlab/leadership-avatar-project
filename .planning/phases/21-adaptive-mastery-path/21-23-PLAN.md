<objective>
Build the coached session's server-side runtime and its single HTTP entry point:
the path step.

Purpose: this is the capability the phase goal states most directly — "coaching
that arrives DURING practice rather than only in the report afterwards", and
21-CONTEXT.md's "a separate mode where the avatar is your coach and you practice
improving upon situations where you previously didn't perform as well as you
could."

As planned before this revision, it did not exist. 21-12 built
`createCoachedSession` / `readCoachedSession` / `finishCoachedSession`; 21-16
built `techniquesForCompetency`, `assertTipSafe` and `recordCoachedContribution`.
All six had zero callers. What shipped was a validator for tips nobody delivers
and a session nobody can start. REQ-113 and REQ-114 are now worded as "a student
can START" and "a student can COMPLETE" for that reason.

This plan is the server half. 21-24 is the student-facing half. They are split
because the orchestration (leg state, tip gating, finish ordering) and the
session shell UI are independently sized pieces of work, and bundling them would
put both past the context budget.

Output: `lib/study-plan/coached/runtime.ts`, one route, and an entry/ordering
verifier.
</objective>

`lib/study-plan/` that may. 21-06's import guard carries exactly one carve-out,

```ts
export interface CoachedLegView {
  coachedSessionId: string;
  leg: "REPLAY" | "FRESH" | "COMPLETE";
  competencyKey: CompetencyKey;
  /** REPLAY only: the student's own words being reworked, verbatim. */
  replayMoment: { text: string; sourceReportId: string; turnIndex: number } | null;
  /** FRESH only: the new situation exercising the same competency. */
  freshScenarioPrompt: string | null;
  /** Technique reminders for this leg. Every entry has passed the tip gate. */
  tips: Array<{ id: string; name: string; reminder: string }>;
  /** The engine type slug this leg runs over, for the session transport. */
  underlyingTypeSlug: string;
}
```

`enterCoachedStep(args: { userId: string; stepId: string }): Promise<CoachedLegView>`
1. Load the path step joining path → studyPlan → userId, require `kind ===
   "COACHED_SESSION"`. 21-12's `createCoachedSession` re-checks this; checking
   here too is correct, because this function also runs on the RESUME path where
   `createCoachedSession` is not called.
2. If `step.coachedSessionId` is null, select the replay target and CREATE the
   session. This is the step-entry creation 21-08's amended rule 4 exists for: a
   PENDING coached step legitimately carries a null id until a student enters it,
   and 21-12 remains the only creator.
   Selecting the replay target:
   - Find the student's weakest-scoring turn for this step's `competencyKey`
     among the reports the owning study plan was generated from. Choose
     deterministically — lowest normalized dimension score for a dimension that
     maps to this competency, tie-broken by most recent report then lowest turn
     index. Deterministic because the phase's standing constraint is
     deterministic-over-model for anything consequential, and because a student
     who reloads before entering must get the same moment.
   - Build the fresh scenario prompt: a situation exercising the same competency,
     naming no words for the student to say. Generate it with a model call ONLY
     for the scenario text, and run the result through `assertTipSafe` with the
     replayed line as `context.studentLine` before persisting it. A scenario that
     echoes the student's line back is the replay again, not a transfer test.
   - Call `createCoachedSession({ userId, pathStepId: stepId,
     replaySourceReportId, replayTurnIndex, freshScenarioPrompt })`.
3. Fetch the replay moment TEXT. **This is the S3 read 21-12 deliberately pushed
   out of `instance.ts`** so its battery stays credential-free. It belongs here.
   Read the transcript for `replaySourceReportId` through the existing accessor
   (`s3Storage` / `getInterviewTranscript`, whichever the codebase already uses —
   read `lib/study-plan/checks/sources.ts` from 21-25 and use the SAME accessor,
   not a second one), take the turn at `replayTurnIndex`, and return its text
   VERBATIM. Do not trim, re-case, summarize, or re-wrap it. If the transcript or
   turn is missing, throw a named `ReplayMomentUnavailableError` — do not
   substitute a paraphrase, because a paraphrased "your words" is the exact
   failure 21-04's verbatim gate exists to prevent, arriving by a different door.
4. Derive `leg` from the session's stored state the way 21-12's
   `readCoachedSession` does — `COMPLETE` when `completedAt` is set, `FRESH` when
   `reportId` is set, else `REPLAY`. Do NOT add a stored leg column; a derived
   value can never disagree with the data.
5. Populate `tips` via `tipsForLeg` (below).
6. Resolve `underlyingTypeSlug` from the replayed report's `typeSlug`. Assert it
   is a member of `ENGINE_TYPES` and throw if not — and note that reading the
   registry is not registering in it; `ENGINE_TYPES` gains no coached entry, and
   21-12's section 2 guard still asserts that.

`tipsForLeg(args: { competencyKey: CompetencyKey; leg: "REPLAY" | "FRESH";
studentLine: string; max?: number })`
- PRIMARY PATH: return `techniquesForCompetency(competencyKey)` entries, capped
  at `max ?? 3`. These are safe by construction (21-16 Mechanism A) and this is
  the path the runtime should almost always take.
- Then, unconditionally, run `assertTipSafe(reminder, { studentLine })` over
  EVERY tip being returned — including library ones. REQ-115 now requires the
  check run on every tip actually rendered, not only at authoring time, and
  running it on library entries costs nothing while catching a library edit that
  slipped past 21-16's own battery.
- Any tip that throws is DROPPED with a logged warning, not repaired, not
  substituted. Return the survivors. If zero survive, return an empty array —
  a coached session with no tips is a worse session, but a scripted tip
  invalidates the evidence, and 21-16 already records that tradeoff.
- Select deterministically (stable order from the library, not random), so the
  same step entered twice shows the same reminders.

`advanceToFresh(args: { userId: string; coachedSessionId: string; replayReportId:
string }): Promise<CoachedLegView>`
- Requires the session be in `REPLAY`. Throws if already `FRESH` or `COMPLETE` —
  the ordering is LOCKED by 21-CONTEXT.md ("replay first, then fresh") and a
  caller that could skip the replay would make REQ-114 false while the data
  still looked right.
- Records that the replay leg finished. Returns the FRESH view with its own tips.
- There is NO `advanceToReplay` and no way to reach FRESH without REPLAY having
  completed. State that both absences are deliberate.

`completeCoachedSession(args: { userId: string; coachedSessionId: string;
reportId: string }): Promise<{ contributionsWritten: number }>`
- Calls `finishCoachedSession(userId, coachedSessionId, reportId)` (21-12) FIRST —
  it sets `reportId` and `completedAt` and marks the path step COMPLETE.
- THEN calls `recordCoachedContribution({ userId, coachedSessionId })` (21-16).
  The order is mandatory: `recordCoachedContribution` requires `completedAt` and
  `reportId` to be non-null and throws otherwise, so calling it first always
  fails. Write that reason in a comment next to the two calls.
- Each exactly once. Both are individually idempotent (21-12 throws on a second
  finish; 21-16 returns `{ written: 0 }`), so a retry is safe — but do not rely
  on that to call them twice.
- Requires the session be in `FRESH`. A session completed from `REPLAY` would
  evidence only the scaffolded leg.

Create the route. Match the auth and error conventions of
`app/api/study-plans/[planId]/route.ts` exactly.

The URL is keyed by **`stepId`** and that is REQ-113's enforcement expressed in
the routing table: there is no `/api/coached/[sessionId]/start`, no
`/api/practice/coached`, and no route that accepts a type slug. The only way in
is a path step the user owns. Write that in a block comment and say that adding
any sibling entry point would violate REQ-113 — this is the comment a future
contributor needs to read before adding a convenience route.

`POST` — enter the step:
1. Auth, then `enterCoachedStep({ userId, stepId })`.
2. 404 on a missing or non-owned step, and 404 (not 400) when the step's `kind`
   is not `COACHED_SESSION` — a wrong-kind step id is indistinguishable to the
   client from a nonexistent coached step, and saying which it is leaks the
   step's kind.
3. 201 with the `CoachedLegView`. On `ReplayMomentUnavailableError`, 409 with a
   message saying the original session's transcript could not be read — a
   specific, actionable failure, not a 500.
4. `maxDuration` 30: entry makes at most one model call (the fresh scenario) and
   one S3 read.

`GET` — the current leg, for resume and for 21-24's polling:
1. `enterCoachedStep` is safe to call again (it resumes when
   `step.coachedSessionId` is set), but GET must NOT create. Add a
   `createIfMissing: false` option to `enterCoachedStep`, or export a separate
   `readCoachedLeg`, and use it here. Decide in implementation and record which
   in the SUMMARY — but a GET that creates a session is a GET that a browser
   prefetch can start a session with, and that must not be possible.
2. 404 when no session exists yet. The client then POSTs.

`PATCH` — advance or finish, discriminated on a body `action`:
- `{ action: "advance", replayReportId }` → `advanceToFresh`. 409 when the
  session is not in `REPLAY`, with the current leg in the body so the client can
  resynchronize rather than retrying blindly.
- `{ action: "complete", reportId }` → `completeCoachedSession`. 409 when not in
  `FRESH`. 200 with `{ contributionsWritten }` so 21-24 can tell the student their
  mastery moved, which is REQ-116's observable half.
- Any other `action` → 400. Do not default to one of them.

Do NOT accept a `coachedSessionId` from the client on any verb. Resolve it from
the step. An id taken from the body is an id that can belong to someone else, and
the ownership join through the step is what makes that impossible.
