<objective>
Build the path as a child of the study-plan object: bounded at 5-10 steps, one per
plan, newly generated per plan, with old paths left intact and reachable.

Purpose: 21-CONTEXT.md is precise here and each clause is a separate failure mode.
"A child of the study-plan object, not a global queue" — a global queue would
merge two plans' paths and lose which plan asked for what. "Bounded at 5-10
steps" — unbounded, it becomes a backlog nobody finishes. "A new study plan
generates a NEW path; old paths are not discarded and not carried forward" — both
halves matter: discarding loses the record, carrying forward reintroduces stale
steps aimed at a gap the student has since closed.

This plan builds the container and its invariants. 21-14 builds the selection
logic that decides what goes IN the steps; keeping them separate is deliberate,
because the container's invariants must hold regardless of how selection evolves.

Output: `lib/study-plan/path.ts` and a verifier for the four invariants.
</objective>

```ts
export interface PathStepInput {
  position: number;              // 1-based, contiguous
  kind: "KNOWLEDGE_CHECK" | "COACHED_SESSION" | "UNAIDED_SESSION";
  competencyKey: CompetencyKey;
  selectionReason: string;       // REQ-118: stored, not recomputed
  knowledgeCheckId?: string | null;
  coachedSessionId?: string | null;
}
```

`createPath(args: { userId: string; studyPlanId: string; steps: PathStepInput[];
selectionSnapshot: unknown }): Promise<PathWithSteps>`

Validate before writing:
1. OWNERSHIP — `prisma.studyPlan.findFirst({ where: { id: studyPlanId, userId } })`
   must return a row. Throw otherwise. A path is created from an API route, so
   this is the only thing stopping a path being attached to someone else's plan.
2. BOUND — `steps.length` within `PATH_STEP_BOUNDS` inclusive. Throw naming the
   actual count and the bound. The schema deliberately does not enforce this
   (21-03's comment says so), which makes this check the ONLY enforcement — say
   that in a comment so nobody removes it believing the database has it covered.
3. POSITIONS — 1-based, contiguous, no duplicates. Sort-and-compare rather than
   trusting caller order.
4. REFERENCE CONSISTENCY — a `KNOWLEDGE_CHECK` step must carry a
   `knowledgeCheckId` and no `coachedSessionId`; a `COACHED_SESSION` step the
   reverse; an `UNAIDED_SESSION` step neither. A step pointing at the wrong
   artifact renders as the wrong kind of exercise.
5. COMPETENCY — every `competencyKey` is in `COMPETENCIES`.
6. IDEMPOTENCE/CONFLICT — `StudyPlanPath.studyPlanId` is `@unique`, so a second
   create throws a Prisma P2002. Catch it and rethrow a named error
   `PathAlreadyExistsError` with the existing path's id, so the caller can show
   the existing path rather than surfacing a database error code. Do NOT
   overwrite or delete the existing path: that would be "carrying forward" by
   another name.

Write path and steps in ONE `prisma.$transaction` (or a nested `create`), so a
path never exists with zero steps. A zero-step path would pass the 5-10 bound on
read and render as an empty improvement plan.

`readPathForStudyPlan(userId: string, studyPlanId: string): Promise<PathWithSteps | null>`
- Scoped by `userId` in the WHERE clause, not filtered after fetching. Returns
  null when the plan has no path yet, which is the normal state for a plan
  created before this phase — pre-Phase-21 StudyPlan rows have no path and must
  render as "no path" rather than erroring. Note that explicitly: this is the
  REQ-120 backward-compatibility case.
- Steps ordered by `position` ascending.

`markStepComplete(userId: string, stepId: string): Promise<void>`
- Verifies ownership by joining through path → studyPlan → userId.
- Sets `status: "COMPLETE"` and `completedAt`. Throws if already COMPLETE.
- Does NOT touch any other step, and does NOT require steps be completed in
  order. 21-CONTEXT.md rules out unlocking, so an out-of-order completion must
  be permitted — a sequential gate here would be unlocking with a different
  name. Write that reasoning in a comment; it is the kind of "obvious
  improvement" a later contributor would add.

`listPathsForUser(userId: string): Promise<Array<{ pathId; studyPlanId;
studyPlanTitle; generatedAt; stepCount; completeCount }>>`
- Ordered by `generatedAt` descending. Every path the user has ever had, including
  superseded ones — this is how an old path stays reachable. Include
  `studyPlanTitle` so the UI can say which plan owns it, since 21-CONTEXT.md says
  separate paths are reached through their own associated study plan.
- There is no `active` flag and no filtering of old paths. A later contributor
  looking for one will not find it; say in a comment that its absence is
  deliberate.

Create `scripts/verify-path-model.ts` in the house `check()` style.

Factor `createPath`'s validation into an exported pure
`validatePathSteps(steps: PathStepInput[]): string[]` (returning violation

a live client and must be skipped with a printed SKIP line when `DATABASE_URL` is

Section 1 — BOUND. 4 steps → rejected naming the count. 5 → accepted. 10 →
accepted. 11 → rejected. 0 → rejected. Assert the rejection message contains both
`5` and `10`, so the error tells a developer the bound rather than just "invalid".

Section 2 — POSITIONS. Duplicate position → rejected. Gap (1,2,4,5,6) → rejected.
0-based (0..4) → rejected. Shuffled but contiguous → ACCEPTED, since order of the
input array is not the invariant; contiguity of positions is.

Section 3 — KIND/REFERENCE CONSISTENCY. For each of the three kinds, one accepted
case and the two wrong-reference rejections (missing its own id; carrying the
other kind's id). Plus `UNAIDED_SESSION` carrying either id → rejected. Plus an
unknown `competencyKey` → rejected.

Section 4 — OLD PATHS SURVIVE (requires a database; print SKIP if unavailable).
Against a scratch user: create study plan A, create its path, create study plan B,
create its path. Then assert:
- `readPathForStudyPlan(user, A)` still returns A's path with its original

- A's steps' `status` values are unchanged by B's path creation.
- `listPathsForUser(user)` returns BOTH, B first.

  A's completed step is STILL complete and C has no step referencing A's step id.
  This is the concrete form of "not discarded and not carried forward" and the
  assertion that fails if a later plan adds migration-of-progress logic.
- A second `createPath` for study plan A throws `PathAlreadyExistsError` and A's

- `createPath` with a `studyPlanId` belonging to a different user throws.

Section 5 — NO ACTIVE FLAG. Read `lib/study-plan/path.ts` as text and assert it
contains no `isActive`, `isCurrent`, or `supersededAt` identifier, and that

failure mode here is an addition, not a change.
