<objective>
Decide what comes next, deterministically and explainably: weakest competency
first, with the reason recorded.

Purpose: 21-CONTEXT.md locks that "what's next" targets the weakest competency
first and is "deterministic and explainable", and the phase's hard constraint is
deterministic derivation over model judgement for anything consequential. A model
asked "what should this student practise next" would give a plausible,
unreproducible, unarguable answer. A ranking function gives one the student can be
shown and can disagree with.

This is also where the path's 5-10 bound gets satisfied in practice: 21-08 built
the container and enforces the bound; this plan produces step lists that are
already inside it.

TDD because it is a ranking function with defined inputs and outputs, and because
the interesting cases — all-null mastery, exact ties, a single weak competency —
are the ones that produce an embarrassing path if unhandled.

Output: `lib/study-plan/next-step.ts` and a determinism battery.
</objective>

  <behavior>
```ts
export interface StepSelection {
  steps: PathStepInput[];          // 5..10, positions 1..n contiguous
  ranking: Array<{ competencyKey; rank; currentPercent: number | null;
                   lifetimePercent: number | null; tier: EvidenceTier;
                   reason: string }>;
}

export function selectPathSteps(args: {
  mastery: MasteryResult;
  desiredCount: number;            // clamped into PATH_STEP_BOUNDS
  /** Competency keys with no available source moment — cannot host a check or a coached step. */
  unavailableCompetencies?: readonly CompetencyKey[];
}): StepSelection

export function nextStepFor(path: PathWithSteps): { step; reason: string } | null
```

RANKING RULE, applied as a documented ordered comparator so every tie is broken
by a declared rule rather than by `Object.keys` order:

1. Primary — `currentPercent` ascending (weakest current form first). This is the
   "weakest competency first" 21-CONTEXT.md locks.
2. A `NONE`-tier competency (no evidence at all) is ranked as weaker than ANY
   measured competency, and ranked FIRST. State the reasoning: an unmeasured
   competency is the largest unknown, and treating `null` as "not weak" would
   mean a student never gets a step for the thing they have never done — the
   opposite of an adaptive path. Do NOT coerce null to 0 to achieve this; handle
   it as an explicit branch, because coercing would make a never-practised
   competency indistinguishable from a catastrophically-practised one in the
   reason string.
3. Secondary — `lifetimePercent` ascending. Two competencies at the same current
   figure are separated by whether the weakness is long-standing.
4. Tertiary — evidence tier ascending (`NONE` < `THIN` < `EMERGING` <
   `ESTABLISHED`). A thin figure is less trustworthy, so gathering evidence on it
   is worth more than acting on a confident one.
5. Final tie-break — `TIE_BREAK_ORDER`, an exported explicit array of competency
   keys derived from `COMPETENCIES`' `order` field. Export it so the tie-break is
   inspectable and so the battery can assert it. Never fall through to array
   order or to `localeCompare` on the key; both are stable-looking accidents
   rather than decisions.

STEP KIND ASSIGNMENT, deterministic:
- The weakest competency gets a `COACHED_SESSION` step — it is the one where
  reworking a real moment is worth the scaffolding.
- Competencies ranked 2..n get `KNOWLEDGE_CHECK` steps.
- The LAST step is always `UNAIDED_SESSION` on the weakest competency — the
  transfer test. This mirrors coached mode's own replay-then-fresh logic at the
  path level: scaffolded first, unaided last. Record that parallel in a comment.
- A competency in `unavailableCompetencies` cannot host a `COACHED_SESSION` or a
  `KNOWLEDGE_CHECK` (both need a source moment) and is assigned
  `UNAIDED_SESSION` instead, or skipped if that would duplicate the final step.
  Without this, 21-10's zero-survivor generation failure would leave a step
  pointing at nothing.

REASON STRINGS must name the competency LABEL (not its key), the figure that drove
the decision, and the comparison: e.g. `"Audience attunement is your weakest
current competency at 38% (established evidence) — this coached session reworks a
moment where it showed."` and for the null case `"Outcome achievement has no
scored evidence yet, so it is ranked first."` The reason is persisted on the step
by 21-08 and shown to the student by 21-19; a reason saying "selected by the
algorithm" would satisfy the type and defeat the requirement.

COUNT: clamp `desiredCount` into `PATH_STEP_BOUNDS` rather than throwing — a
caller asking for 3 should get 5, because the bound is a product decision and the
caller is usually a default. But if the catalog has fewer competencies than
`PATH_STEP_BOUNDS.min`, steps must repeat the weakest competencies to reach the
minimum rather than returning an out-of-bounds list that 21-08 would reject.
Assert that case in the battery — with 7 competencies and a min of 5 it does not
bite today, but a faculty-authored catalog with 3 competencies would.

`nextStepFor(path)` returns the lowest-`position` step whose `status` is
`PENDING`, with its STORED `selectionReason` — not a recomputed one. Mastery moves
between generation and completion, so recomputing would show the student a reason
that no longer matches the step they were given. Returns null when every step is
COMPLETE or SKIPPED. Does NOT skip ahead and does NOT gate on earlier steps: the
first pending step by position, regardless of what came before, because 21-CONTEXT.md
rules out unlocking.

  <implementation>
RED: write `scripts/verify-next-step.ts` first. Build `MasteryResult` literals (no
database, no clock) and assert:
- SINGLE WEAKEST: six competencies at 80% and one at 30% → rank 1 is the 30% one,
  it gets the `COACHED_SESSION`, and the final step is `UNAIDED_SESSION` on it.
- ALL NULL: every competency unmeasured → ranking follows `TIE_BREAK_ORDER`
  exactly, and every reason string says "no scored evidence yet".
- NULL BEATS MEASURED: one competency at 2% measured, another unmeasured → the
  unmeasured one ranks first. Then assert the two reason strings DIFFER in kind,
  proving null was not coerced to 0.
- EXACT TIE: two competencies with identical current, lifetime and tier → ordered
  by `TIE_BREAK_ORDER`. Then shuffle the input `competencies` array and assert
  the identical result. This is the determinism assertion.
- DETERMINISM: call twice on the same input → deep-equal, including reason strings.
- BOUNDS: `desiredCount: 2` → 5 steps. `desiredCount: 40` → 10 steps.
  `desiredCount: 7` → 7. Every result's positions contiguous from 1, and every
  result accepted by 21-08's `validatePathSteps`. Assert that last one by actually
  calling it — the two plans' contracts must be proven to meet, not assumed to.
- UNAVAILABLE: weakest competency in `unavailableCompetencies` → it gets no
  `KNOWLEDGE_CHECK` and no `COACHED_SESSION`, and the result is still a valid
  5-10 step list.
- SMALL CATALOG: a synthetic 3-competency mastery result → still produces at
  least 5 steps, with repeats, still passing `validatePathSteps`.
- REASON QUALITY: every reason string contains the competency's LABEL and, when
  the figure is non-null, a percent sign. Assert no reason string is shorter than
  40 characters — a cheap proxy that catches a placeholder.
- `nextStepFor`: all-pending path → position 1 with its stored reason. Position 1
  COMPLETE, 2 PENDING → returns 2. Position 1 PENDING, 2 COMPLETE → returns 1
  (out-of-order completion does not advance the pointer past a pending step).
  All complete → null. Assert the returned reason is the STORED string by seeding
  a step with a recognizable sentinel reason and checking it comes back verbatim.
Run it; fails. Commit `test(21-14): add failing weakest-first selection battery`.
