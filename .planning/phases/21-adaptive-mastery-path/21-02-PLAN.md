First enumerate the ground truth. The scored dimensions today are
`SHARED_RUBRIC_DIMENSION_KEYS` (`visual`, `vocal`, `content`, `behavioral`) plus
each type's `extraRubricDimensions`. As of this phase those extras are:

- deck family (`lib/pitch/deck-rubric.ts` SHARED_DECK_DIMENSIONS):
  `deck_structure`, `deck_text_density`, `deck_visual_quality`,
  `slide_speech_correlation`
- talk (`lib/pitch/talk-type.ts`): `audience_takeaway_clarity`, `holding_the_room`

- product (`lib/pitch/product-type.ts`): `objection_handling`
- deck/investor (`lib/pitch/deck-type.ts`): `negotiation`
- funding (`lib/pitch/funding-type.ts`): `use_of_funds_credibility`,
  `ask_feasibility`
- networking (`lib/networking/prompts.ts` NETWORKING_RUBRIC_EXTRAS): `rapport`,
  `self-introduction`, `goal-progress`
- difficult-conversation (`lib/difficult-conversation/conversation-type.ts`):
  `clarity`, `empathy`, `holding_the_line`, `objective_achieved`

Re-derive this list in code at module load — do NOT hardcode the list above as
the source of truth. Export `allRubricDimensionKeys(): string[]` that reads
`SHARED_RUBRIC_DIMENSION_KEYS` and iterates `ENGINE_TYPES` from
`lib/engine/registry.ts`, collecting `extraRubricDimensions[].key`, deduped and
sorted. The list above is the EXPECTED output and belongs in a comment so a
reviewer can see what was derived, not in the data path. This is what makes the
catalog self-maintaining when Phase 22 adds a type.

Then define the grouping. Export:

```ts
export interface Competency {
  key: CompetencyKey;
  label: string;
  /** What a student is being told they are good or bad at. Shown in the UI. */
  description: string;
  /** Rubric dimension keys that evidence this competency. */
  dimensionKeys: readonly string[];
  /** Display order in the breakdown. */
  order: number;
}
```

Group the 22 dimensions into SEVEN competencies (discretion exercised here; the
grouping rationale goes in a block comment):

1. `delivery_presence` — `visual`, `vocal`, `holding_the_room` — how the student
   shows up: body, voice, command of the room.
2. `structure_and_clarity` — `content`, `clarity`, `deck_structure`,
   `audience_takeaway_clarity` — whether the point lands in an order that builds.
3. `concision_and_focus` — `conciseness` has no dimension key; use `concision`,
   `deck_text_density` — saying it tightly, on one slide or in one breath.
4. `audience_attunement` — `behavioral`, `empathy`, `rapport`,
   `discovery_tailoring`, `self-introduction` — reading the person in front of
   them and shaping to them.
5. `holding_position_under_pressure` — `holding_the_line`, `objection_handling`,
   `negotiation` — keeping the ask intact when pushed.
6. `credibility_of_the_case` — `use_of_funds_credibility`, `ask_feasibility`,
   `deck_visual_quality`, `slide_speech_correlation` — whether the claim and its
   support hold up.
7. `outcome_achievement` — `objective_achieved`, `goal-progress` — whether the
   student got what they came for.

Export `COMPETENCIES: readonly Competency[]`, and derive
`DIMENSION_TO_COMPETENCY: ReadonlyMap<string, CompetencyKey>` FROM `COMPETENCIES`
by inverting `dimensionKeys` — never maintain both lists by hand. Throw at module
load if inversion finds a dimension key claimed by two competencies; a dimension
contributing to two competencies would double-count it in mastery arithmetic.

Export `competencyForDimension(key: string): CompetencyKey | null`, returning
null rather than throwing, so the verifier can report the full set of unmapped
keys instead of dying on the first.

Add an exported `COMPETENCY_CATALOG_SOURCE = "derived-from-rubric-dimensions"`
const and a block comment stating the replaceability seam REQ-103 requires:
consumers must import `COMPETENCIES` / `competencyForDimension` and must never
switch on a dimension key directly, so swapping in a faculty-authored catalog is
one file's change. Name that constraint in the comment — a later framework sets
this const to `"faculty-authored"` and replaces the catalog body only.

Do NOT edit any file under `lib/engine/` or `lib/pitch/` or
`lib/difficult-conversation/`. This plan reads them.

<task type="auto">
  <name>Task 2: Write the totality verifier with a deliberately-unmapped negative case</name>
  <files>scripts/verify-competency-catalog.ts</files>
  <action>
Create `scripts/verify-competency-catalog.ts` following the shape of
`scripts/verify-engine-config.ts` — a `check(label, condition)` counter, a final
pass/fail summary, `process.exit(1)` on any failure.

Assert, against the REAL registry (not a fixture):

1. Totality: for every key in `allRubricDimensionKeys()`,
   `competencyForDimension(key)` is non-null. On failure, print EVERY unmapped
   key, not just the first — this is the message a future phase author will read.
2. No orphans in the other direction: every key listed in any competency's
   `dimensionKeys` appears in `allRubricDimensionKeys()`. A competency claiming a
   dimension that no longer exists is stale catalog, and it silently reduces
   evidence counts instead of erroring.
3. No double-claim: `DIMENSION_TO_COMPETENCY.size` equals the total length of all
   `dimensionKeys` arrays summed. If a key were claimed twice, the map would be
   smaller.
4. Every competency has at least one dimension. A zero-evidence competency would
   render a permanently-thin figure no session can ever improve.
5. `order` values are unique and contiguous from 1.
6. Spot-check the cross-type requirement concretely: at least three competencies
   draw dimensions from more than one interaction type. Compute "which types
   declare this dimension" from `ENGINE_TYPES` to prove it. This is the
   assertion that fails if someone later refactors the catalog into per-type
   silos, which 21-CONTEXT.md explicitly forbids.
7. NEGATIVE CASE — the guard must be proven to bite. Construct a local synthetic
   dimension list `[...allRubricDimensionKeys(), "__phantom_dimension__"]` and
   assert the totality check applied to THAT list fails. Factor the totality
   logic into a local `findUnmapped(keys: string[])` helper so both the real and
   the synthetic case run through the same code. Without this, a vacuously-true
   verifier passes forever.
  </action>
  <verify>`npx tsx scripts/verify-competency-catalog.ts` exits 0 and prints a check count of at least 7 with the negative case reported as an expected failure that was correctly detected.</verify>
  <done>The verifier passes against the real registry, prints every unmapped key on failure, and proves its own totality check bites via a synthetic phantom dimension.</done>
</task>
