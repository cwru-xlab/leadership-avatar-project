<objective>
Model the four knowledge-check formats inside the study-plan surface, and prove
mechanically that doing so did not make knowledge checks an engine interaction
type.

Purpose: 21-CONTEXT.md is explicit — all four formats ship; they live INSIDE
`lib/study-plan/` as path steps; they do NOT become a registered engine
interaction type; smallest footprint, no engine involvement. The temptation is
real: the engine already has type records, rubric dimensions, evaluators and
session plumbing, so routing checks through it would feel like reuse. It would
also drag the avatar session shell, the rubric schema and the termination policy
into a multiple-choice question. The guard in this plan is what keeps a later
refactor from doing it quietly.

Output: `lib/study-plan/checks/types.ts` with validated per-format payloads, and
a verifier carrying the no-engine-registry negative guard.
</objective>

<task type="auto">
  <name>Task 1: Model and validate the four check payloads</name>
  <files>lib/study-plan/checks/types.ts</files>
  <action>
Create `lib/study-plan/checks/types.ts`. Follow the validation conventions already
in `lib/study-plan/types.ts` — a `LIMITS` const, small `readString` /
`readArray` / `isRecord` helpers, and throw-with-a-label on violation. Reuse that
file's helpers by exporting them from it if they are not already exported;
otherwise reimplement locally rather than editing `types.ts`'s existing exports,
and say which route was taken in the SUMMARY. Do not change any existing export's
behaviour — the existing study-plan surface must keep working (REQ-120).

Export `CHECK_FORMATS = ["MULTIPLE_CHOICE", "FILL_IN_BLANK",
"PICK_BETTER_RESPONSE", "REWRITE_WEAK_LINE"] as const` and `type CheckFormat`.

Per-format payload interfaces, discriminated on `format`:

`MultipleChoicePayload` — `options: string[]` (exactly 4, each 1..240 chars, all
distinct after NFC normalization; a duplicate option makes two answers correct).
Answer key: `{ correctIndex: number }`, 0..3.

`FillInBlankPayload` — `segments: string[]` and `blankCount: number`, where
`segments.length === blankCount + 1` so the rendered prompt interleaves
unambiguously. 1..3 blanks. Answer key:
`{ accepted: string[][] }` — one array of accepted strings per blank, so a blank
can accept synonyms. Each accepted string 1..80 chars, at least one per blank.

`PickBetterResponsePayload` — `candidates: [string, string]` (exactly two, each
1..600 chars, distinct) plus `rationalePrompt: string | null`. Answer key:
`{ betterIndex: 0 | 1 }`. Note in a comment that one candidate SHOULD be the
student's own verbatim line and the other a constructed alternative — but this
module does not enforce which, because 21-10 owns generation and the verbatim
guarantee. Cross-referencing it here would duplicate the gate in two places.

`RewriteWeakLinePayload` — `weakLine: string` (the student's own line, 12..600
chars — the 12 floor matches `MIN_QUOTABLE_LENGTH` exported by
`lib/study-plan/verbatim.ts`; import it, do not restate the number),
`techniqueHint: string` (the skill to apply — names the technique, never the
words), `rubricCriteria: string[]` (1..4 criteria a model grader scores against).
Answer key: `null`. This format has NO deterministic key.

Export `validateCheckPayload(format: CheckFormat, value: unknown): CheckPayload`
and `validateAnswerKey(format: CheckFormat, value: unknown): AnswerKey | null`.
`validateAnswerKey` MUST throw if a non-null key is supplied for
`REWRITE_WEAK_LINE`, and MUST throw if null is supplied for any of the other
three. That asymmetry is REQ-111's deterministic/model split made structural
rather than conventional.

Export `isDeterministicFormat(format: CheckFormat): boolean` returning true for
the first three. Export
`CONTRIBUTION_SOURCE_FOR_FORMAT(format): "CHECK_DETERMINISTIC" | "CHECK_MODEL_GRADED"`
derived FROM `isDeterministicFormat`, not from a second hand-maintained map —
this is the single point where a format's weight class is decided, and 21-11 and
21-15 both read it.

Export nothing that mentions the engine, imports from `lib/engine/`, or declares
a `typeSlug`. A block comment must state why: REQ-108 keeps knowledge checks out
of the engine registry, and an engine import here would be the first step toward
the refactor the next task's guard forbids.
  </action>
  <verify>`npx tsc --noEmit` clean. `grep -c "lib/engine\|@/lib/engine" lib/study-plan/checks/types.ts` returns 0. `npx tsx -e "import {validateAnswerKey} from './lib/study-plan/checks/types'; validateAnswerKey('REWRITE_WEAK_LINE', {x:1})"` throws.</verify>
  <done>Four payload interfaces with per-field limits, validators that throw naming the field, a non-null answer key rejected for REWRITE_WEAK_LINE and null rejected for the other three, the weight class derived from one predicate, and zero engine imports.</done>
</task>

<task type="auto">
  <name>Task 2: Battery plus the no-engine-registry negative guard</name>
  <files>scripts/verify-knowledge-check-surface.ts</files>
  <action>
Create `scripts/verify-knowledge-check-surface.ts` in the house `check()` style.
Model the surface-count guard on `scripts/verify-engine-surface-count.ts` and
`scripts/verify-dc-surface-count.ts`, which already exist for exactly this kind

Section 1 — payload validation. For each of the four formats, one ACCEPT case and
at least three REJECT cases, asserting the thrown message names the offending
field:
- MULTIPLE_CHOICE: 3 options; 5 options; two identical options; `correctIndex: 4`.
- FILL_IN_BLANK: `segments.length !== blankCount + 1`; `blankCount: 0`;
  `blankCount: 4`; a blank with an empty `accepted` array.
- PICK_BETTER_RESPONSE: one candidate; three candidates; two identical
  candidates; `betterIndex: 2`.
- REWRITE_WEAK_LINE: an 8-character `weakLine` (below the imported
  `MIN_QUOTABLE_LENGTH`); empty `rubricCriteria`; 5 `rubricCriteria`; a non-null
  answer key.
- And the inverse: null answer key rejected for each of the first three formats.

Section 2 — THE GUARD. Import `ENGINE_TYPES` from `lib/engine/registry.ts` and
assert:
- No entry's `slug` is a member of `CHECK_FORMATS` (case-insensitively, and with
  underscores normalized to hyphens, so `MULTIPLE_CHOICE` would also catch a
  `multiple-choice` slug).
- No entry's `slug` or `label` contains `knowledge`, `quiz`, or `check`.
- `ENGINE_TYPES.length` equals the count recorded by the existing engine
  surface-count verifier. Read that expected number from whichever existing
  verifier declares it rather than restating it, so the two cannot drift. If it
  is not exported, assert against a local const and note in the SUMMARY that the
  number is duplicated and where.
- Nothing under `lib/study-plan/` imports from `lib/engine/` — **with ONE
  enumerated carve-out: `lib/study-plan/coached/**`.** Walk the directory, read
  each `.ts` file, skip any path matching `lib/study-plan/coached/`, and assert
  no `from "@/lib/engine` or `from "../engine` occurrence in the rest. The
  carve-out is NOT a weakening and must be implemented as an explicit,
  single-entry exclusion list (`const ENGINE_IMPORT_CARVE_OUTS = ["lib/study-plan/coached/"]`)
  with a comment naming
  `.planning/phases/21-adaptive-mastery-path/21-COACHED-ENGINE-DECISION.md` as
  its authority, so a reader can see exactly what is exempt and why.

  Why: 21-12's recorded DECISION is that coached mode **reuses the engine's live
  session machinery** (a coached session IS a live avatar conversation) while
  staying out of `ENGINE_TYPES`, and 21-23/21-24 build that runtime under
  `lib/study-plan/coached/`. Without the carve-out this guard starts failing the
  moment the coached runtime lands, and the tempting "fix" is to weaken the whole
  walk — losing the assertion that actually matters.

  What 21-CONTEXT.md actually locks is "no engine involvement" **about knowledge
  checks**. So keep the assertion ABSOLUTE for `lib/study-plan/checks/**` and for
  every file at the top level of `lib/study-plan/`, and assert that separately
  and by name, so the two claims cannot be collapsed into one weaker one:
  - absolute, no exceptions: any file under `lib/study-plan/checks/` or directly
    in `lib/study-plan/` imports nothing from `lib/engine/`
  - carved out, by the named decision only: `lib/study-plan/coached/` may
  Also assert the carve-out list has EXACTLY one entry. A second entry appearing
  later is how this guard would quietly become meaningless, and the count
  assertion makes adding one a deliberate, reviewed act.

Section 3 — INVERTED ASSERTION for the guard. Factor section 2's slug check into
