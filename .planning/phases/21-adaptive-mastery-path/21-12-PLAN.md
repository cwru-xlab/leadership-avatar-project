<objective>
Create coached practice as its own instance, reachable only through a study plan's
path, structured replay-first-then-fresh — and write down, explicitly, what its
relationship to the engine is.

Purpose: 21-CONTEXT.md gives the user's framing verbatim — "not accessible
through typical practice modes. so it's not like you're adding a coach to an
interview, it's like a separate mode where the avatar is your coach and you
practice improving upon situations where you previously didn't perform as well as
you could." Normal practice sessions are UNTOUCHED. That is both a feature
decision and the thing that keeps REQ-85 un-violated: Phase 18 forbids a
disengagement indicator in a graded practice session, and coaching never appears
in one.

The planning constraint also demands that coached mode's engine relationship be
decided and justified explicitly rather than drifting. 21-06 forbade knowledge
checks from the engine registry; coached mode is genuinely different, because it
IS a live avatar session. Deciding it in a document, in this plan, is what keeps
a later contributor from registering it as a sixteenth interaction type because
that seemed tidier.

Output: `lib/study-plan/coached/instance.ts`, a written engine decision, and an
isolation verifier.
</objective>

  <files>.planning/phases/21-adaptive-mastery-path/21-COACHED-ENGINE-DECISION.md</files>
  <action>
Write the decision document the phase constraint requires. Do this BEFORE Task 2,
because Task 2's imports must follow it rather than the document rationalizing
whatever got written.

Investigate first, then decide and record:
- What `InteractionTypeConfig` requires of a registered type (`lib/engine/types.ts`):
  rubric dimensions, an evaluator prompt, a live system prompt builder, an
  instance config, a termination policy. Enumerate which of these a coached
  session genuinely has and which it does not.
- What registering a type costs: it appears in the type picker, it is reachable
  from `app/practice/[type]`, it gains `avatarMayEnd` / `avatarEndFloor` /
  disengagement semantics, and it shows up in the surface-count verifiers. Note
  that appearing in the picker ALONE would violate REQ-113.

Then record the DECISION, which is: coached mode **reuses the engine's live
session machinery but is NOT a registered `ENGINE_TYPES` entry.** It runs as a
session over the competency's underlying interaction type — the same type the
original moment came from — with a coach layer supplied by
`lib/study-plan/coached/`. Justify each half:
- Not registered, because registration is what makes a type reachable from the
  practice picker, and REQ-113 requires it be reachable ONLY through a path step.
  A registered-but-hidden type is a surface that one routing change exposes.
- Reuses the machinery, because a coached session IS a live avatar conversation
  and reimplementing session transport, transcript capture and evaluation would
  fork the exact plumbing Phase 13 unified. 21-06's "no engine involvement"
  constraint was written about knowledge checks specifically — a multiple-choice
  question has nothing in common with a session — and must not be
  over-generalized to coached mode. Say that explicitly, because the two
  constraints look contradictory read side by side.

Then record the CONSEQUENCES that follow, each as a binding statement:
- A coached session produces a normal `InteractionReport` so it is scored by the
  existing evaluator; its contribution is recorded at the COACHED_SESSION weight
  (21-16), which is what keeps it from counting as unaided practice.
- Phase 18's disengagement machinery: state whether coached sessions enable a
  disengagement threshold. Decide NO — a coach does not walk out — and record
  that this is why REQ-85's amendment is a boundary clarification and not a
  behaviour change. The coach's guidance is not a disengagement indicator, and
  the coached session does not carry one either.
- A coached session's report must be distinguishable from an unaided one at read
  time, or mastery cannot weight them differently. State the mechanism:
  `CoachedSession.reportId` is the join, and 21-16 reads it.

Finally record what was REJECTED and why: registering a `coached-practice` type
in `ENGINE_TYPES`; adding a coach flag to `ResolvedSessionConfig`; and adding
coaching to normal practice sessions (the Deferred-list item — note that adding
it later is a GENUINE REQ-85 conflict requiring its own decision, per
21-CONTEXT.md).
  </action>

  <done>The engine relationship is decided in writing with both halves justified, the apparent contradiction with 21-06's constraint is addressed head-on, the disengagement question is answered NO with its REQ-85 consequence stated, and three rejected alternatives are recorded.</done>

<task type="auto">
  <name>Task 2: Build path-step-only coached session creation with replay-then-fresh structure</name>
  <files>lib/study-plan/coached/instance.ts</files>
  <action>
Create `lib/study-plan/coached/instance.ts`, implementing the decision from Task 1.

Export `COACHED_PHASES = ["REPLAY", "FRESH"] as const`. The order is LOCKED by
21-CONTEXT.md — "replay first, then fresh. The coach sets up the actual moment
from the student's transcript to rework, then presents a new situation exercising
the same competency — learn it, then prove it transfers." Mark the ordering
locked in a comment, distinct from the provisional numbers elsewhere in the phase.

`createCoachedSession(args: { userId: string; pathStepId: string;
replaySourceReportId: string; replayTurnIndex: number; freshScenarioPrompt:
string }): Promise<CoachedSessionView>`

Enforce, in order:
1. THE ONLY ENTRY. Load the path step by id, joining path → studyPlan → userId,
   and require: the row exists, `userId` matches, and `kind ===
   "COACHED_SESSION"`. Throw `NotReachableOutsideAPathError` otherwise. There is
   no overload, no optional `pathStepId`, and no "standalone" variant — write a
   comment saying all three absences are deliberate and are what REQ-113 means.
   The function signature itself is the guard: `pathStepId` is required and
   non-nullable.
2. REPLAY IS MANDATORY. `replaySourceReportId` must name an `InteractionReport`
   owned by `userId`, and `replayTurnIndex` must be a non-negative integer within
   that report's `turnCount`. Throw otherwise. A coached session without a real
   moment to rework is a generic practice session wearing the coach's label, and
   it would quietly become the thing 21-CONTEXT.md rules out.
3. FRESH IS MANDATORY. `freshScenarioPrompt` non-empty, within a declared length
   limit. Both phases must exist at creation; a session cannot be created with
   only one.
4. ONE PER STEP. `CoachedSession.pathStepId` is `@unique` (21-03). Catch P2002 and
   return the existing session rather than erroring, so a double-click resumes
   instead of failing — and write the step's `coachedSessionId` back in the same
   transaction so `path.ts`'s kind/reference consistency check stays satisfied.

`readCoachedSession(userId, coachedSessionId): Promise<CoachedSessionView | null>`
- Scoped by `userId` in the WHERE clause.
- `CoachedSessionView` carries `phase: "REPLAY" | "FRESH" | "COMPLETE"` DERIVED
  from stored state, not stored as a fourth column: `COMPLETE` when
  `completedAt` is set, `FRESH` when `reportId` is set (the fresh leg is the one
  that produces the gradeable session), else `REPLAY`. Deriving it means the
  phase can never disagree with the data; a stored phase column would eventually.
- Includes the replay moment's text, fetched by the CALLER and passed in, or
  exposed as a separate accessor — do NOT read S3 inside this module. Keeping
  I/O out is what let 21-04's and 21-09's batteries run credential-free, and the
  same should hold here.

`finishCoachedSession(userId, coachedSessionId, reportId): Promise<void>`
- Verifies ownership, sets `reportId` and `completedAt`, and marks the owning
  path step COMPLETE via `markStepComplete` (21-08) in one transaction. Throws if
  already complete.
- Does NOT record a mastery contribution. 21-16 owns that, because the coached
  weight and the tip-compliance check belong together. Note the split explicitly
  so neither plan records it twice — a double contribution would make coached
  practice count more than unaided, inverting the locked ordering.
  </action>
