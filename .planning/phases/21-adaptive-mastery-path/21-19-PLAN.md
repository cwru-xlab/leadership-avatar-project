  <files>app/api/study-plans/[planId]/path/route.ts</files>
  <action>
Create the route alongside the existing `app/api/study-plans/[planId]/route.ts`,
matching its auth and response conventions exactly.

`GET`:
1. `readPathForStudyPlan(currentUser.id, planId)`. Null → 200 with
   `{ path: null }`, NOT 404. A plan without a path is a normal state (every
   pre-Phase-21 plan), and a 404 would make the client treat a valid plan as
   missing. Comment this.
2. Resolve each step's artifact for display: for a `KNOWLEDGE_CHECK` step, the
   check's `format`, `prompt` and whether an attempt exists; for a
   `COACHED_SESSION` step, the coached session's derived phase. Return the
   STORED `selectionReason` verbatim on every step — never recompute it.
3. Call `nextStepFor(path)` and return `nextStep` with its reason.
4. Return a narrow DTO. Do NOT return `KnowledgeCheck.answerKey` — shipping the
   answer key to the browser would let a student read the answer from the network
   tab, and the three closed formats are graded server-side precisely so that
   does not have to happen. Assert this in Task 4. Also omit `quotedText`'s
   source report internals beyond the id, and omit `selectionSnapshot` (it is a
   frozen mastery record for auditing, not display).

`POST` — generate the path for this plan:
1. Load mastery: `readContributions` → `computeMastery` → identify competencies
   whose checks cannot be generated. Determine `unavailableCompetencies` by
   attempting check generation (21-10) per selected competency and collecting the
   ones that returned `ok: false`, OR by pre-checking which competencies have
   usable moments. Choose the pre-check: generating first and discarding wastes
   model calls and makes the request slow and non-deterministic in cost. Comment
   the choice.
2. `selectPathSteps({ mastery, desiredCount, unavailableCompetencies })`.
3. For each `KNOWLEDGE_CHECK` step, call `generateChecksForCompetency` (21-10) and
   attach the resulting check id. If a generation returns `ok: false`, convert
   that step to `UNAIDED_SESSION` rather than failing the whole request — but
   record the conversion in the response as `degradedSteps`, so a systematically
   failing generator is visible rather than silently producing paths of plain
   sessions. For a `COACHED_SESSION` step, create the step first and let
   `createCoachedSession` be called later from the step itself (21-12 requires an
   existing step), leaving `coachedSessionId` null at creation — then the step's
   kind/reference rule in 21-08 must permit a COACHED_SESSION step with a null
   id at creation time. Verify that it does; if 21-08 requires it non-null,
   create the coached session inside the same transaction instead. State which
   route was taken in the SUMMARY — this is the one genuine integration seam
   between 21-08 and 21-12 and it must not be guessed at.
4. `createPath(...)`. On `PathAlreadyExistsError`, return 409 with the existing
   path id. Do NOT regenerate or replace — 21-CONTEXT.md requires a new path come
   from a new STUDY PLAN, not from re-posting to an existing one.
5. `maxDuration` raised to 60 like the existing generate route, since this makes
   several model calls.
6. 201 on success with the path DTO and `degradedSteps`.
  </action>
