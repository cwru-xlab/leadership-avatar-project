<objective>
Make coach tips technique reminders only — enforced mechanically — and record a
completed coached session's mastery contribution at the coached weight.

Purpose: 21-CONTEXT.md states it plainly: "Tips are TECHNIQUE REMINDERS ONLY.
Name the skill; never script the words. The student's words stay theirs, which is
what lets a coached session evidence anything at all." That last clause is the
load-bearing one. If the coach feeds the student a line and the student says it,
the resulting score measures the coach. The whole case for coached sessions
moving mastery at all rests on the tip not being the answer.

The phase's deterministic-over-model constraint applies directly: a prompt saying
"do not script the words" is not enforcement. This plan builds the check that
rejects a scripted tip before the student sees it.

Output: `lib/study-plan/coached/tips.ts`, `lib/study-plan/coached/contribution.ts`,
and a rejection battery.
</objective>

  <files>lib/study-plan/coached/tips.ts</files>
  <action>
Create `lib/study-plan/coached/tips.ts`.

TWO MECHANISMS, and the first is the stronger one — lead with it.

MECHANISM A — a CLOSED technique library. Export
`TECHNIQUE_LIBRARY: ReadonlyArray<{ id: string; competencyKey: CompetencyKey;
name: string; reminder: string }>`, with 3-5 techniques per competency covering
all seven from `COMPETENCIES`. Each `reminder` is one sentence naming what to DO,
in the second person, with no quoted speech: e.g. for
`holding_position_under_pressure`, `{ name: "Restate the ask",
reminder: "Say the ask again in the same words you used the first time, before
you respond to the objection." }` — it instructs a move, not a line. For
`structure_and_clarity`, `{ name: "Headline first", reminder: "Lead with your
conclusion, then give at most two supports." }`.

A tip drawn from this library is safe BY CONSTRUCTION, because a human wrote it
and a verifier checks it. Make this the primary path: the coach SELECTS a
technique id, and the rendered tip is the library's `reminder` text. Export
`techniquesForCompetency(key)` for the selector. Document that this is the
preferred mechanism and that Mechanism B exists for the case where a tip must
reference the student's specific moment.

MECHANISM B — `validateTip(tip: string, context: { studentLine: string }):
TipValidation`, for any tip text not drawn verbatim from the library. Returns
`{ ok: true }` or `{ ok: false; reason: TipRejectReason; detail: string }` with
`TIP_REJECT_REASONS`:
- `CONTAINS_QUOTED_SPEECH` — the tip contains a double-quoted, single-quoted, or
  curly-quoted span of 4+ words. A quoted span in a coaching tip is a line to
  say; there is no benign use of it here.
- `CONTAINS_SCRIPT_CUE` — the tip matches a scripted-line lead-in from a declared
  phrase list: `try saying`, `say something like`, `you could say`, `respond with`,
  `tell them`, `use this`, `for example:`, `here's how to phrase`, `instead say`,
  `word it as`. Keep the list as an exported const array so it is reviewable and
  extensible in one place, and match case-insensitively on word boundaries.
- `CONTAINS_FIRST_PERSON_LINE` — the tip contains a first-person declarative of
  6+ words (a sentence starting with `I ` / `I'm` / `I'd` / `My ` / `We `). The
  coach speaks in the second person about what the student should DO; a
  first-person sentence is the coach drafting the student's speech. This is the
  rule that catches an unquoted script, which is the form the other two miss.
- `TOO_LONG` — over 240 characters. A technique reminder is a sentence. A
  paragraph is either a script or a lecture, and length is the cheapest reliable
  proxy. Export the limit as a named const marked PROVISIONAL UNTIL CALIBRATED.
- `ECHOES_STUDENT_LINE` — the tip contains a 6+ word span from
  `context.studentLine`. The coach may NAME the moment but must not re-perform
  it; a tip that quotes the student back at them is the replay, not a technique.

Document the FALSE-POSITIVE risk honestly in a block comment: this rejector will
occasionally refuse a legitimate tip (a technique named with a quoted term of
art, for instance). That tradeoff is chosen deliberately — a rejected good tip
costs one regeneration, an accepted scripted tip invalidates the session's
evidence. Record the mitigation: the library in Mechanism A exists precisely so
the common path never touches the rejector.

Also export `assertTipSafe(tip, context)` that throws on rejection, for the
call site that must not proceed. The non-throwing form is for the generator that
wants to discard-and-retry; the throwing form is for anything rendering to the
student.

  <name>Task 2: Record the coached contribution at the coached weight</name>
  <files>lib/study-plan/coached/contribution.ts</files>
  <action>
Create `lib/study-plan/coached/contribution.ts`.

`recordCoachedContribution(args: { userId: string; coachedSessionId: string }):
Promise<{ written: number }>`

21-12 deliberately left this out of `finishCoachedSession` so the coached weight
and the tip rules live together. This is the SINGLE writer of
`COACHED_SESSION`-sourced contributions — say so in a block comment and name
21-12's `finishCoachedSession` as the function that must NOT also write one. A
double write would make a coached session contribute more than an unaided one,
inverting the ordering REQ-107 locks.

Steps:
1. Load the `CoachedSession` scoped by `userId`. Require `completedAt` non-null
   and `reportId` non-null. Throw otherwise — a session with no report has no
   scores, and writing a contribution from nothing would be fabricated evidence.
2. **Do NOT reimplement the report→competency mapping here.** Call
   `contributionsFromReport({ userId, reportId: session.reportId, source:
   "COACHED_SESSION", occurredAt: session.completedAt })` from
   `lib/mastery/from-report.ts`, built by **21-21**. That module is the SINGLE
   home of the mapping (REQ-124) and is shared with LIVE_SESSION ingestion. Two
   copies of this arithmetic would make coached and live contributions stop being
   comparable, which is exactly what the weight ordering depends on.

   `from-report.ts` already does, and this plan must NOT restate: the
   `asScoreMap` read from `lib/report/snapshot.ts`; the `competencyForDimension`
   map-up (21-02); the `(score - 1) / 4` normalization shared with 21-11's
   rewrite grader; and the null-is-not-zero skip (a null `visual` score means
   camera off or insufficient data per Phase 10's `visualUnscoredReason`, not a
   visual failure, and a competency whose every dimension is null yields NO
   contribution rather than a zero).
3. Pass the returned `ContributionInput[]` straight to `recordContributions`.
   This plan's remaining responsibility is the three things that are genuinely
   coached-specific: the `COACHED_SESSION` source constant, the
   `completedAt`/`reportId` preconditions in step 1, and the idempotence guard in
   step 4. ONE contribution per competency — assert the count equals the number of
   competencies `contributionsFromReport` returned.
4. IDEMPOTENCE. Before writing, check whether any contribution already exists
   with this `sourceReportId` and `source: "COACHED_SESSION"`. If so, return
   `{ written: 0 }` without writing.

   NOTE the matching half of this, which lives in 21-21 and not here: this
   guard keys on `source: "COACHED_SESSION"`, so it CANNOT suppress a
   `LIVE_SESSION` row for the same report — and a coached session's report does
   flip to READY and does fire 21-21's live ingestion hook. The protection
   against a coached session contributing 1.00 + 0.40 is 21-21's unconditional
   `skipped: "coached-session"` check in `recordLiveSessionContributions`, which
   returns early for any report joined to a `CoachedSession`. Do not duplicate
   that check here and do not rely on this guard to do its job; just record in
   the SUMMARY that the coached row written here is the session's ONLY
   contribution. A retried finish must not double-count, and
   the ledger has no unique constraint for this (21-03 did not add one, because
   a legitimate re-grade is conceivable) — so the guard lives here. Say that.

Also export a short comment block recording the weighting consequence for
auditability: because `source` is stored on every row and `weight` is
snapshotted, a reader can confirm after the fact that coached rows carry 0.40 and
live rows carry 1.00. That is what makes REQ-116's "weighted below unaided
practice" checkable in production data and not only in a verifier.

Section 1 — LIBRARY COVERAGE AND SAFETY. For every competency in `COMPETENCIES`,
assert at least 3 techniques exist. Then run EVERY library `reminder` through
`validateTip` with an arbitrary `studentLine` and assert ALL pass. A library

is cheap to prevent. Also assert no reminder contains a double quote character at
all, and that every reminder is under the length limit.

Section 2 — REJECTION CASES. One per reason, plus a near-miss that must PASS:
- `CONTAINS_QUOTED_SPEECH`: `Try this: "I understand your concern but the
  deadline is fixed"` → reject. Near-miss that passes: `Use the "name it, claim
  it" move.` — a 3-word quoted term of art, under the 4-word threshold.
- `CONTAINS_SCRIPT_CUE`: one case for each phrase in the exported list, asserting
  every phrase actually fires. A phrase in the list that never matches is dead
  config, and iterating the list in the test is how that gets caught.
- `CONTAINS_FIRST_PERSON_LINE`: `I hear you, and the decision still stands.` →
  reject. Near-miss that passes: `I'd focus on pacing.` — 4 words, under the
  6-word threshold, and clearly coach-voice. Assert it passes, so the rule is
  shown to be scoped rather than blanket.
- `TOO_LONG`: a 300-character tip → reject.
- `ECHOES_STUDENT_LINE`: student said `I think we should probably push the
  deadline back a bit`; tip contains `we should probably push the deadline` →
  reject. Near-miss that passes: a tip containing only `push the deadline`
  (3 words) → pass.
- Assert `assertTipSafe` THROWS on each rejection case and does not throw on each
  passing case.

Section 3 — WEIGHT ORDERING, asserted here as well as in 21-05. Assert
`CONTRIBUTION_WEIGHTS.LIVE_SESSION > CONTRIBUTION_WEIGHTS.COACHED_SESSION`. This
is the file a contributor would touch if they decided coached sessions should
count fully, so the guard belongs here too.

Section 4 — CONTRIBUTION (database). On a scratch user: a study plan, a path with
a COACHED_SESSION step, a coached session, and an `InteractionReport` with a
hand-written `scores` JSON covering several dimensions including one null.
Assert:
- `recordCoachedContribution` writes one row per competency with at least one
  non-null dimension, and the competency whose dimensions are all null gets NO
  row.
- Every written row has `source: "COACHED_SESSION"` and
  `weight === CONTRIBUTION_WEIGHTS.COACHED_SESSION`.
- A second call returns `{ written: 0 }` and the row count is unchanged.
- Calling it on a session with `completedAt: null` throws and writes nothing.
- Calling it with a different `userId` throws.
- Compute mastery before and after and assert the figures moved, so the
  contribution is proven to reach the computation and not merely the table.
- Then write an equivalent `LIVE_SESSION` contribution with the SAME `rawScore`
  for the same competency and assert the recomputed figure sits closer to the
  live score than to the coached one — the concrete proof that the coached
  weighting is actually below unaided in the arithmetic, not just in the table.
Clean up in a `finally`.
