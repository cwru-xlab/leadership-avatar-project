Camera-on selection flow, in this order:
1. `GET /api/metrics/consent` (once, cached in state). If `acceptedAt` is null,
   render `MetricsConsentDialog` with `open`. Its `onDecline` sets
   `cameraMode: "OFF"` and closes — a real path, never a dead end. Its

   and continues to step 2.
2. Probe the camera with `requestCameraStream()` from
   `lib/metrics/visual-capture.ts`. **Immediately stop the probe's tracks** —
   this is a permission and availability check, not the session stream; the
   shell requests its own. Leaving the probe stream live would hold the camera
   LED on through the wizard.
3. On `{ ok: false, reason }`, set `cameraBlock` and render a BLOCK panel in

   this site. Allow it in your browser's site settings, then try again."
   `NOT_FOUND`: "We couldn't find a camera on this device."
   `UNAVAILABLE`: "Your camera is in use by another app. Close it and try
   again."), a "Try again" button re-running the probe, and a prominent
   "Continue with my camera off" button that sets `cameraMode: "OFF"`, clears
   the block and proceeds. The student is never trapped and is never silently
   downgraded — both are explicit CONTEXT.md requirements.
4. On `{ ok: true }`, `setStep("session")`.

Camera-off selection proceeds straight to `session` with a short inline notice
(not a modal) that Visual and Vocal will not be scored this time.

  <name>Task 2: Capture lifecycle and live affordances in the session shell</name>

  <action>
Add `cameraMode: CameraMode` to `InterviewSessionShellProps` (`:53-70`). No
setter, no toggle, no UI anywhere in this component that could change it —

Refs: `visualCaptureRef`, `vocalCaptureRef`, `cameraStreamRef`, and
`const [faceMissing, setFaceMissing] = useState(false)`.

**Visual capture start.** In `handleAvatarStateChange` (`:459-467`), where the
existing code reacts to `StreamingAvatarSessionState.CONNECTED` by calling
`startOpening()`, additionally — and only when `cameraMode === "ON"` — call
`requestCameraStream()`, store the stream, create the capture with
`onFaceStateChange: (detected) => setFaceMissing(!detected)`, and `start()` it.
Start capture AFTER the avatar has connected, not before: a camera-on session
must never delay the avatar handshake (REQ-49), and the landmarker's several-MB
dynamic import would otherwise compete with the WebRTC setup.

If `requestCameraStream()` fails here despite the wizard's successful probe (the
camera was seized between steps), do NOT block — the student is already in a
live session and blocking would destroy it. Show one `addToast` warning that
Visual won't be measured, leave `visualCaptureRef` null, and let the finish
payload's null visual block resolve to `INSUFFICIENT_DATA` on the server. That
is the honest outcome and it is exactly why REQ-42's discriminator exists.

**Vocal capture.** Create the vocal capture handle on mount (camera-mode
independent — audio is always available). Call `attachStream(stream)` inside the
existing `getMicrophone()` (`:468-477`) right after the stream is obtained, so
it reuses the same audio stream the push-to-talk already gets. Do NOT add a
second `getUserMedia({ audio: true })` call and do NOT modify the existing
`startMetering` function — the vocal engine runs its own independent
`AnalyserNode` (plan 10-04) and the existing peak-RMS guard for rejecting silent
recordings must keep working byte-identically.

In `transcribeRecording` (`:510+`), after the existing duration/bytes/peak-RMS
guards pass and the blob is built, call
`vocalCaptureRef.current?.submitSpokenTurn(audio, elapsed)` — fire-and-forget,
BEFORE or in parallel with the existing `/api/audio/transcribe` fetch, never
awaited, so the live transcription latency the student feels is unchanged. If a
recording is rejected by one of those guards, do NOT submit it: a rejected blob
is not a spoken turn.

Wherever a typed answer is sent (the text input's submit path feeding
`sendMessage`), call `vocalCaptureRef.current?.recordTypedTurn()`. Locate it by
reading the code rather than guessing — the shell has both a push-to-talk path
and a text input, and only the text path may call this.

**Live affordances.** Render `<SelfViewThumbnail stream={cameraStreamRef.current} />`
and `<FaceDetectionBanner visible={cameraMode === "ON" && faceMissing} />` inside
the session's full-screen container. Both are fixed-position and
`pointer-events-none`, so place them as siblings after the existing layout
rather than inside the avatar's own container — they must not affect the
existing flex/grid geometry or intercept clicks on the mic button or the
End/Leave controls. With `cameraMode === "OFF"` the thumbnail receives a null
stream and renders nothing and the banner is never visible.

**Finish.** In `handleEnd` (`:643+`), immediately before the existing
`fetch("/api/interview/session/finish")` at `:680`:
```ts
const visual = visualCaptureRef.current?.stop() ?? null;
const vocal = (await vocalCaptureRef.current?.drain(8000)) ?? null;
```
and add `metrics: { cameraMode, visual, vocal }` to the existing request body.
Note the ordering: `drain` is awaited (bounded at 8s by plan 10-04's design) and
`stop()` is synchronous. Show the existing in-flight spinner state across the
drain so the End button does not look frozen.

Preserve `handleEnd`'s existing structure exactly: it still reads
`reportIdRef.current` directly and never calls `ensureReport()` from an exit path
(the 06-06 decision preventing orphan IN_PROGRESS rows); the avatar session is
still stopped only AFTER a successful or 409 finish response (the 06-06 decision
that a network failure leaves a live, retryable interview); the confirm modals
and the under-3-answers warning are unchanged. If `drain` somehow throws, catch
it and send `metrics` with nulls rather than losing the interview.

**Cleanup.** In the existing unmount/teardown effect, stop the visual capture,
`detachStream()` the vocal capture, and stop every track on
`cameraStreamRef.current` — the camera LED must go out when the session ends,
including on a Leave. Leaving a camera track live after the page changes is both
a privacy problem and a support complaint.
