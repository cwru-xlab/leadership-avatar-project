```ts
const transcription = await openai.audio.transcriptions.create({

});
```

<task type="auto">
  <name>Task 2: The vocal capture engine</name>
  <files>lib/metrics/vocal-capture.ts</files>
  <action>
Create `lib/metrics/vocal-capture.ts`. Browser-only, but no browser API at
module scope. Export
`createVocalCapture(): VocalCaptureHandle` where
```ts
type VocalCaptureHandle = {
  attachStream(stream: MediaStream): void;      // begins/refreshes RMS metering
  beginTurnRecording(): void;                    // marks the start of a spoken turn
  submitSpokenTurn(audio: Blob, elapsedMs: number): void; // fire-and-forget word analysis
  recordTypedTurn(): void;
  detachStream(): void;
  drain(timeoutMs?: number): Promise<VocalMetrics | null>;
};
```

**RMS series (volume consistency + pauses).** Extend the pattern already proven
at `components/interview/InterviewSessionShell.tsx:472-508` — an `AnalyserNode`
with `fftSize: 2048` polled on a `setInterval`, reading
`getFloatTimeDomainData`. Do not replace or refactor that existing code; this is
a parallel, independent instance owned by this module. Differences:
- Poll every 100ms (not 50) — half the work of the existing meter, which matters
  for REQ-49 given the tab is also running the visual engine and a WebRTC stream.
- Push each sample's RMS into a rolling array capped at 12000 entries (20
  minutes) — plain numbers, never audio buffers.
- `volume_consistency`: over samples above a speech floor (RMS >= 0.01),
  compute `1 - min(1, stdDev / max(mean, 1e-6))` — i.e. one minus the
  coefficient of variation, clamped to [0, 1], so 1 means perfectly steady.
  Return 0 when there are fewer than 20 above-floor samples.
- Wrap the whole Web Audio setup in try/catch exactly as the existing
  `startMetering` does; on failure set an `audioMeterError` flag and continue —
  word-timing metrics can still succeed without the meter.

**Pause count.** Derive pauses from WORD GAPS, not from RMS: for each analysed
turn's word list, count consecutive-word gaps where
`words[i+1].start - words[i].end >= 1.5` seconds. Only gaps WITHIN a turn
count — a gap between turns is the interviewer speaking, not the student
pausing, and counting it would be a fabricated metric. Document this. Sum across
turns.

**Words per minute.** `totalAnalysedWords / (totalAnalysedSpokenSeconds / 60)`,
where `totalAnalysedSpokenSeconds` sums each analysed turn's `durationSec` from
the route. Never use session wall-clock as the denominator — that would divide
the student's speech by time the interviewer was talking and produce a number
that looks measured but is not. Return 0 when no turn was analysed.

**Filler words.** Lowercase and strip punctuation from each word token, then
match against `FILLER_WORD_LEXICON` from `lib/metrics/types.ts` — single tokens
by equality and multi-word entries by consecutive-sequence match, consuming the
matched tokens so `you know` is not also counted as two hits. Accumulate
`filler_word_count` and a deduplicated `filler_word_list` of the distinct
fillers actually observed (cap the list at 12 entries). Note in a comment that
`whisper-1` retains disfluencies more faithfully than `gpt-4o-transcribe`,
which is a second reason this route cannot be folded into the existing one.

**Per-turn submission (the latency design — this is the Q3 resolution).**
`submitSpokenTurn` increments `spokenTurns`, adds the turn's measured duration,
and fires the `/api/audio/word-metrics` POST WITHOUT awaiting it, storing the
promise in a pending set. When it resolves, merge its words into the aggregate
and increment `analysedTurns`; on rejection, leave `analysedTurns` unincremented
(this is the vocal liveness signal `resolveVocalOutcome` reads). Because each
call overlaps the interviewer's own response time, word analysis is complete
long before the session ends and adds ZERO latency to the evaluation path —
which is why the single-`status` polling model in both report pages stays
untouched. Put that rationale in a file-level comment.

`recordTypedTurn()` increments `typedTurns` only. It must not touch
`spokenTurns`, `spokenSeconds`, or any metric numerator — REQ-44: typing is a
different modality, never a penalty. Add an explicit comment that this is
deliberately not symmetric with the camera case.

`drain(timeoutMs = 8000)`:
- Awaits all pending word-metrics promises with `Promise.allSettled` under a
  bounded race against `timeoutMs`. A turn that has not resolved by then is
  simply not merged and not counted as analysed — never a thrown error and never
  a blocked End button.
- Returns a `VocalMetrics` with `coverage` = `{ spoken_turns, typed_turns, analyzed_turns, spoken_seconds, analyzer_error }`,
  where `analyzer_error` is true if `audioMeterError` is set AND no turn was
  analysed (i.e. nothing at all worked). A meter failure alone is not a
  technical failure of the whole vocal pipeline — word metrics are the primary
  signal.
- Returns `null` if neither `attachStream` nor any turn was ever recorded.

Zero persistence: no `localStorage`, no `sessionStorage`, no IndexedDB, no
retained `Blob` beyond the in-flight `fetch` body.

   Time one real `runAndPersistEvaluation`-shaped call via a throwaway script
   against an existing READY report's transcript, as `08-04-SUMMARY.md` did.

Then record the DECISION in the SUMMARY, explicitly:

- **Primary design (expected outcome): keep the single-`status` polling model.**
  Per-turn word analysis runs DURING the session and overlaps the interviewer's
  own turn latency, so by session end the aggregate is already complete
  client-side. `drain(8000)` bounds the worst case. The finish request carries
  the finished metrics object, the runner attaches it to the evaluator's user
  message, and metrics land in the SAME `READY` write as content/behavioral.
  Nothing is added to the 50s evaluation budget, and neither report page's
  polling changes. This is why plan 10-02 deliberately left
  `REPORT_TERMINAL_STATUSES` alone.

- **Explicit fallback, only if the measurement contradicts the above** — i.e. if
  a single turn's word-metrics call routinely exceeds ~15s (so per-turn calls
  cannot keep pace with a brisk conversation) or if `drain(8000)` would
  routinely drop more than a third of turns: add a `metricsStatus String?`
  column to both report models (a fifth migration), have the finish route write
  `metricsStatus: "PENDING"` and resolve it independently of `status`, extend
  both DTOs with `metrics.status`, and have both report pages continue polling
  while `metrics.status === "PENDING"` even after `status === "READY"` — with
  their give-up timers reset accordingly. Write this out as a concrete
  gap-closure plan sketch in the SUMMARY if and only if the measurement triggers
  it, and flag it for `/gsd:plan-phase 10 --gaps`.

Do not implement the fallback speculatively.
