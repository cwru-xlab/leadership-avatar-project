Build the consent record and its dialog, and persist the locked camera mode plus
a consent snapshot onto both report rows at session start.

informed consent about being *analysed*, and that the decision is remembered.

the report — which only works if the mode is written server-side at row
creation, following the Phase 8 snapshot discipline, rather than inferred later
from whether metrics happened to arrive.

session-start route.
</objective>

  <name>Task 1: Consent record and endpoint</name>
  <files>app/api/metrics/consent/route.ts, middleware.ts</files>
  <action>
Create `app/api/metrics/consent/route.ts`. Copy the auth and `response()`
scaffolding verbatim from `app/api/interview/session/start/route.ts`.
`export const runtime = "nodejs"`.

`GET` — returns `{ acceptedAt: string | null }` read from
`User.videoAnalysisConsentAt` (the column added by plan 10-02) for the current
user only. Never accepts a userId from the client.

`POST` — sets `videoAnalysisConsentAt` to `new Date()` for the current user if
it is currently null, and returns `{ acceptedAt }`. Idempotent: an already-
accepted user gets their EXISTING timestamp back unchanged, never a refreshed
one — the record is "when they first accepted", and silently bumping it would
destroy the audit value the timestamp exists for. Accepts no body fields at all;
ignore anything sent. There is deliberately NO revoke endpoint: CONTEXT.md
scopes this phase to acceptance, and a revoke flow would need its own decision
about in-flight sessions.

Log only `{ userId, firstAccept: boolean }`.

In `middleware.ts`, add `"/api/metrics"` to `STUDENT_ROUTES` — exactly one line,
mirroring 09-02's single `"/api/scenario"` addition. Do NOT touch
`ADMIN_ROUTES` and do not reorder existing entries. Note that, as with every
sibling route in this repo, an unauthenticated call will hit middleware's
pre-existing 307 redirect-to-`/login` rather than a JSON 401 — that is the
already-logged behaviour from `06-08-SUMMARY.md`, not something to fix here.
  </action>
