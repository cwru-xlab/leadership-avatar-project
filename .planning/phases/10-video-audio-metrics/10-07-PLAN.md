them and record why a category went unscored.

  <name>Task 1: Ingest the metrics payload at finish, in both routes</name>
  <files>app/api/interview/session/finish/route.ts, app/api/scenario/session/finish/route.ts</files>
  <action>
Add a shared, strict validator. Put it in `lib/metrics/ingest.ts` — a NEW file
in the `lib/metrics/` module this phase owns, so the two routes cannot drift:
`export function parseMetricsPayload(value: unknown): { visual: VisualMetrics | null; vocal: VocalMetrics | null }`.

Rules, all deliberate:
- Accept only the `SessionMetricsPayload` shape from `lib/metrics/types.ts`. Any
  missing, malformed, or extra-typed input yields `{visual: null, vocal: null}` —
  never a throw and never a 400. A client that fails to send metrics must still
  be able to finish its session; the resulting null simply becomes
  `INSUFFICIENT_DATA` downstream, which is the honest outcome.
- **Reject anything media-shaped, structurally.** Walk the parsed object and
  reject the whole block if any value is a string longer than 64 characters, or
  matches `/^data:|^blob:|^https?:/`, or if the serialized payload exceeds 8KB.
  The only strings that legitimately appear are short posture flags and short
  filler words. This is REQ-38 enforced by the server rather than trusted from
  the client — a compromised or buggy client cannot smuggle a frame through this
  door. Comment it as such.
- Clamp every numeric field into its documented range (percentages 0-100,
  `volume_consistency` 0-1, counts >= 0) and coerce `NaN`/`Infinity` to 0. A
  metric that arrives out of range is a client bug, not a licence to store a
  nonsense number the evaluator will then reason about.
- Drop any `posture_flags` entry not in `VISUAL_POSTURE_FLAGS`, and cap
  `filler_word_list` at 12 entries.
- Do NOT read `cameraMode` from this payload. The camera mode is already on the
  row from plan 10-05, written at creation and never mutated — accepting it
  again here would create a second, client-controlled write path and break
  REQ-35's lock. Comment that explicitly.

In `app/api/interview/session/finish/route.ts`: read an optional `metrics` field
from the existing destructured body (`:57-60`), run it through
`parseMetricsPayload`, and add `visualMetrics` / `vocalMetrics` to the EXISTING
`prisma.interviewReport.update` that flips `IN_PROGRESS -> PENDING` at `:134-142`.
Store `null` for an absent block, not `{}`.

Change nothing else: keep the transcript-save-before-PENDING ordering (a failed
S3 write must still leave the row `IN_PROGRESS` and return 502, `:118-132`), the
409 double-submit branch (`:82-93`), the 400 on an empty transcript, the
`waitUntil(runAndPersistEvaluation(...))` call, and the 202 response shape. The
request path must stay LLM-free and fast — do not compute or fetch anything new
here.

Make the identical change in `app/api/scenario/session/finish/route.ts` against
its own `prisma.scenarioReport.update`, preserving its 409 branch, its S3 log
completion, and its `waitUntil(runAndPersistScenarioEvaluation(...))`.
  </action>

  <action>
Extend the `prisma.interviewReport.findFirst`/`select` that loads the row to
also fetch `cameraMode`, `visualMetrics` and `vocalMetrics`.

Parse the two `Json?` columns back into the shared types using `asVisualMetrics`
/ `asVocalMetrics` exported from the `lib/metrics/ingest.ts` created in Task 1 —
not a third private copy. (Plan 10-02's DTO-local helpers stay as they are: they
run in the client-facing mapping layer and were written before this module
existed. Note the small duplication in the SUMMARY as a deliberate, recorded
choice rather than silently refactoring a file this plan does not own.)

Before calling `runInterviewEvaluation`, resolve outcomes with the plan 10-01
discriminator:
```ts
const visualOutcome = resolveVisualOutcome((report.cameraMode as CameraMode | null) ?? "OFF", visual);
const vocalOutcome = resolveVocalOutcome(vocal);
```
Note the `?? "OFF"`: a legacy row has a null `cameraMode`, and treating it as
camera-off yields `CAMERA_OFF_OPTOUT` — but the report page must render legacy
rows as "Not yet measured", so **do not write an unscored reason when
`report.cameraMode === null`**. Leave both reason columns null for such a row.
That single condition is what keeps REQ-48 and REQ-45 from colliding, and it
belongs in this file with a comment, not in the report page's rendering logic.

Pass metrics to the evaluator ONLY when the outcome says scored:
`visualMetrics: visualOutcome.scored ? visual : null` and the vocal analogue.
This is the research's Pitfall-3 guard: a technical failure must not send a
metrics object the model would then dutifully score. The prompt's own
missing-data rule then returns null for that category, and plan 10-06's gate
makes the code agree.

In the `outcome.ok` branch, replace the hardcoded
`visualScore: null, vocalScore: null` at `:93-94` with
`visualScore: outcome.result.visualScore, vocalScore: outcome.result.vocalScore`,
and add to the same update:
- `visualUnscoredReason: report.cameraMode === null ? null : visualOutcome.reason`
- `vocalUnscoredReason: report.cameraMode === null ? null : vocalOutcome.reason`
Write them in the SAME `status: "READY"` update as the content/behavioral scores
and the markdown. One write, one status transition — which is precisely why
neither report page's polling needs to change (plan 10-02 deliberately left
`REPORT_TERMINAL_STATUSES` alone; plan 10-04 measured that this fits the budget).

In `persistFailure`, do NOT write metric columns. A FAILED evaluation leaves the
metrics as ingested and the reasons null — the existing "Not scored" state
already covers "evaluation ran and produced nothing", and that is a fourth,
separate cause (REQ-45) which must not be overwritten by a metrics reason.

Add `cameraMode`, `visualUnscoredReason` and `vocalUnscoredReason` to the
existing `console.info("Interview evaluation completed", ...)` payload. Do not
log the metrics objects themselves.

Leave the `roleContext` fallback chain (`report.roleTitle ?? preset... ??
DEFAULT_INTERVIEW_TYPE`, `:74-80`), the transcript-missing FAILED path, and the
catch-all best-effort FAILED write exactly as they are.
  </action>
