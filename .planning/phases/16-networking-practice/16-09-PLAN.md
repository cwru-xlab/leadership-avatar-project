<objective>
Prove, on real turns of a real session, that the student's goal never reaches the
avatar — and that it does reach the evaluator. Then prove the avatar's floor-gated
walk-away and the outcome record work in practice.

Purpose: 16-CONTEXT.md's Specific Ideas call the hidden goal "the design centerpiece",
and a leak here is a SILENT correctness failure — the session still runs, the report
still renders, and Goal Progress quietly becomes unmeasurable because the avatar
pre-empted the student's work. This is Phase 16's analogue of Phase 14's investor-pitch
leak test (`14-13-PLAN.md`), and it is load-bearing evidence for criterion 4.
Output: one exhaustive leak script and one recorded real-session test record. NO product
code changes — a failure here is a recorded gap, not an inline fix.
</objective>

  <action>
Create `scripts/verify-networking-goal-leak.ts` in the house style (numbered sections,
prints each assertion, non-zero exit on failure). Use one sentinel constant at the top.
Assert, covering the full set of assembly functions identified in
`<blocking_dependency>`:

1. **Resolution carries the goal.** `resolveSessionConfig("networking", …)` with the
   sentinel goal in the customization resolves `ok: true` and the sentinel is retrievable
   from the resolved session state. (If the goal never reaches resolution, the rest of
   the test is vacuous — this section proves the test is live.)
2. **System prompt, every turn.** For turns 1, 2, 3, 5, 10 and 30, the real system-prompt
   assembly function returns a string with no occurrence of the sentinel, and no
   occurrence of `/goal|objective|what they want|their ask/i`. Print the turn-1 prompt in
   full so a human can read what the avatar actually gets.
3. **Tail block, every turn.** Same turns, same assertion, against the real tail-block
   builder. Print turn 1 and turn 5's tail blocks.
4. **The whole outbound body.** Build the complete provider request body the live turn
   endpoint sends (same function, same inputs — including message history) and assert the
   sentinel appears nowhere in `JSON.stringify(body)`. Do this for a 1-message history, a
   10-message history and a history where the STUDENT themselves mentioned something
   goal-adjacent. Print the key set of the body.
5. **The visible-context slice.** `applyVisibleContext(networking.visibleContext, state,
   turn)` for the same turns: `JSON.stringify` of the slice contains no sentinel.
6. **The slice is not bypassable by a new channel.** Add an UNDECLARED channel to the
   session state carrying the sentinel and assert it is still absent from the slice. This
   is the assertion that proves the allow-list posture 16-07 chose (record the result even
   if 16-07 used a deny-list — in that case this section is EXPECTED to leak, and that
   expected leak must be recorded as a known risk rather than silently passed).
7. **The evaluator DOES see it.** `buildNetworkingEvaluationContext(resolved, snapshot)`
   contains the sentinel. Print it. Without this, Goal Progress is unscoreable and the
   exclusion has gone too far.
8. **The snapshot stores it.** A networking `inputSnapshot` built from the same session
   carries the sentinel in `goal`, and `asInputSnapshot` round-trips it.
9. **No other type is affected.** The same sentinel placed in an interview session's
   customization behaves exactly as it did before Phase 16 — print the result; this guards
   against the networking exclusion being implemented as a global filter.
10. **Grep backstop.** Repo-wide (excluding `.planning/` and this script), no file under
    `lib/engine/` reads a `goal` field. `grep -rn "\.goal\b" lib/engine/` returns nothing.
    The goal is per-type data; the engine must not know the word.
