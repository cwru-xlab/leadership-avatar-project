  <name>Task 1: POST /api/interview/session/start — create the IN_PROGRESS row</name>
  <files>app/api/interview/session/start/route.ts</files>
  <action>
Create the route with `export const runtime = "nodejs";` and a local `response(body, status)`
helper that sets `Cache-Control: no-store`, exactly as `upload-resume/route.ts` does.

Request body (JSON):
```ts
{
  typeSlug: string;
  interviewerAvatarId?: string | null;
  interviewerName?: string | null;
  resumeId?: string | null;
  resumeText?: string | null;
}
```

Validation:
- Auth first → 401 `{ error: "Unauthorized" }` on no user.
- `getInterviewType(typeSlug)` from `@/lib/interview/types`; null → 400
  `{ error: "Unknown interview type" }`.
- `resumeId`, if present, must match a UUID v4 regex; otherwise ignore it (set null) — it is
  client-supplied and is never allowed to shape an S3 key downstream.
- `resumeText`, if present, must be a string; truncate to 60000 chars before storing. This is
  the reproducibility snapshot the evaluator needs. Never return it in the response.
- `interviewerName` truncate to 200 chars; `interviewerAvatarId` truncate to 200 chars.

Create:
```ts
const report = await prisma.interviewReport.create({
  data: {
    userId: currentUser.id,
    typeSlug: type.slug,          // canonical slug from the registry, not raw input
    interviewerAvatarId, interviewerName,
    resumeId, resumeText,
    status: "IN_PROGRESS",
  },
  select: { id: true },
});
```

Respond `201` with `{ reportId: report.id }` ONLY. Never echo back resumeText or any S3 key.

Wrap in try/catch; log `console.error("Interview session start failed:", error)` and return
500 `{ error: "Unable to start the interview session." }`. Log success with
`console.info("Interview report created", { userId, reportId, typeSlug })` — no resume text.

<task type="auto">
  <name>Task 2: POST /api/interview/session/checkpoint — persist the transcript to S3</name>
  <files>app/api/interview/session/checkpoint/route.ts</files>
  <action>
Same `runtime = "nodejs"`, same auth pattern, same `no-store` response helper.

Request body:
```ts
{ reportId: string; turns: unknown; progress: InterviewProgress; }
```
There is deliberately NO `startedAt` in the request body. The authoritative start time is the
`startedAt` column on the report row (step 6), so a client-supplied one would only ever be
discarded. Do not declare it — 06-06 builds its checkpoint body from this shape and must not
send a field the server throws away.

Flow:
1. Auth → 401.
2. `reportId` must match a UUID regex → 400 if not. This guard is what keeps client input out
   of the S3 key even though `sanitizePathSegment` also rejects bad segments.
3. Ownership fetch:
   ```ts
   const report = await prisma.interviewReport.findFirst({
     where: { id: reportId, userId: currentUser.id },
     select: { id: true, status: true, typeSlug: true, interviewerAvatarId: true, interviewerName: true, startedAt: true },
   });
   ```
   Null → **404** `{ error: "Not found" }`.
4. If `report.status !== "IN_PROGRESS"` → 409 `{ error: "This interview has already been submitted." }`.
   A late checkpoint must never overwrite the transcript a PENDING/READY evaluation is reading.
5. `normalizeTurns(body.turns)` from `@/lib/interview/transcript`. Empty array → 400.
6. Build the transcript with `buildInterviewTranscript({ reportId, userId: currentUser.id, typeSlug: report.typeSlug, interviewer: { avatarId: report.interviewerAvatarId, name: report.interviewerName }, startedAt: <report.startedAt.getTime()>, turns, progress })`.
   Use the DB `startedAt`, not the client's — the client value is untrusted.
   Sanity-check `progress`: if it is not an object, substitute `initialProgress()`.
7. `await s3Storage.saveInterviewTranscript(currentUser.id, report.id, transcript)`.
8. Update `turnCount` and `transcriptKey` on the row:
   `await prisma.interviewReport.update({ where: { id: report.id }, data: { turnCount: turns.length, transcriptKey: key } })`.
9. Respond `200` with `{ ok: true, turnCount: turns.length }`.

Keep this route lean — it fires after every assistant turn (~9-15 times per interview) and the
client calls it fire-and-forget. Do no LLM work, no S3 reads, and no extra queries here.

On error: log and return 502 `{ error: "Checkpoint failed" }`. The client ignores the failure
by design; do not make this route retry internally.
