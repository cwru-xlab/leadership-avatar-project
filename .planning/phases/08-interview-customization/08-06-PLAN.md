<objective>
Wire the picker's resolved customization through the wizard into the live session, and
make the client-side progress tracker honor the chosen session length.

`session/start` and every chat turn unchanged. REQ-21 is only satisfied when the
client's own stage machine stops assuming the 20-minute / 9-question shape —

"Quick" session march through the same stages as a 30-minute one.

<task type="auto">
  <name>Task 3: Make the client progress tracker length-aware</name>
  <files>components/interview/InterviewSessionShell.tsx</files>
  <action>
`advanceProgress(previous, hasResume)` hardcodes the stage machine to a ~9-question
shape: the resume stage advances at `questionsAsked >= 3` and the behavioral stage
advances once `categoriesCovered.length >= 3`. Neither reads `targetQuestionCount`, so
every non-`standard` length silently gets the `general` preset's shape.

Decision for this phase (explicit, not implicit): derive the thresholds from
`targetQuestionCount` rather than relying on the time-based closing trigger alone. Give
`advanceProgress` a third parameter `targetQuestionCount: number` and compute:
- `resumeQuestionCap = hasResume ? Math.max(1, Math.round(targetQuestionCount / 3)) : 0`
  — replaces the literal `3` in the resume branch
- `behavioralCategoryQuota = Math.max(2, Math.round(targetQuestionCount / 3))`, clamped
  to at most `BEHAVIORAL_CATEGORIES.length` — replaces the literal `3` in the
  behavioral branch
For the 9-question `standard` length these must both evaluate to 3, so the shipped,
human-validated `general` path behaves EXACTLY as it does today. Assert that in the
verification below — it is the single most important check in this task.

Pass `interviewType.targetQuestionCount` at the call site. Keep the opening,
role_specific and closing branches as they are.

`buildProgressBlock`'s time-based "move to closing" line remains the real backstop and
needs no change (it already takes `targetMinutes` from the resolved type). Add a
comment above `advanceProgress` recording both facts: thresholds now scale with the
chosen length, and the time target remains the backstop.

Also confirm the session header readout `{progress.questionsAsked} of ~{interviewType.targetQuestionCount} questions`
now reflects the customized count — it already reads from `interviewType`, so this is a
verification point rather than an edit.
